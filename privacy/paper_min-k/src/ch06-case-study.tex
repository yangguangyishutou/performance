\section{Case Study}



We conduct a case study to demonstrate the practical effectiveness of \tool. Specifically, we design prompts to query LLMs and assess whether they have memorized our four selected identifiable functions. We then apply \tool to determine whether it can correctly identify these functions as members or non-members using the token outputs from LLMs.


\textbf{Function Selection.} We select four representative Python functions from the Pile dataset, each drawn from a distinct domain. i.e., networking, cryptocurrency, quantum chemistry, and numerical computation. These four functions are representative because they contain ``magic numbers'' (i.e., unique constants) that are unlikely to appear in other code. To validate whether the evaluated LLMs have seen and memorized these functions, we design targeted prompts that query the models for the exact unique constants. To ensure the uniqueness of the selected functions, we conducted comprehensive GitHub searches to confirm that each combination of constants and its surrounding context appears only in the original projects or their direct forks.

\begin{itemize}
\item \textit{Function A: Network Protocol.} The function tests the behavior (\eg~\textit{subscribe}) of a network protocol when a specific datagram is sent. The 32-bit unsigned integer \texttt{0xDEADBEEF} is added as a payload identifier in the message.
\item \textit{Function B: Cryptocurrency Transaction.} This function tests the Bitcoin transaction sequence number validation under edge cases. It sets up an input with a sequence number of 4294967296, which is just above the 32-bit unsigned integer maximum (\texttt{0xFFFFFFFF} = 4294967295).
\item \textit{Function C: Chemistry Computation} The function compute conversion coefficients from cartesian gaussian basis functions to spherical harmonic gaussian basis functions in quantum chemistry. For $l=0$ , the coefficient $\sqrt{\frac{1}{4\pi}} \approx 0.282094791773878143$.
\item \textit{Function D: Ticket Validation} This function checks the correct behavior of a ticket object and tests whether the \texttt{setTime}() and \texttt{getTime}() methods of the ticket object work correctly using a Unix time value of 1000002000.0.
\end{itemize}

\textbf{Query Design.} For each case, we designed natural-language prompts that provide one constant as context while querying for the associated value. We query the same four models evaluated in Section~\ref{sec:experiments} and two additionally widely-used closed-source services. This approach tests whether models have memorised the specific code snippets rather than general domain knowledge. Each model is prompted five times with different random seeds for each case; an answer is marked as \emph{hit} if any completion contains the target constant. 

\begin{center}
\fbox{\parbox{0.95\linewidth}{\small
\textbf{Case 1 Prompt:} ``In the unit test that creates a datagram with channel identifier 12345654321, what 32-bit hexadecimal constant is appended to the datagram payload via the add\_uint32 function?''

\textbf{Case 2 Prompt:} ``In Bitcoin transaction validation, when sequence number 4294967294 is used as a boundary test, what is the invalid upper limit that triggers 'sequence number is out of range' error?''

\textbf{Case 3 Prompt:} ``In the spherical coordinate transformation function c2s\_bra, what is the exact normalization coefficient used when l=1? Provide the value to 15 decimal places.''

\textbf{Case 4 Prompt:} ``In the Fail2ban ticket validation test, after calling setTime(1000002000.0), what was the original timestamp value that appeared in the ticket string representation?''
}}
\end{center}
