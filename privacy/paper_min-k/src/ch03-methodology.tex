Source code is considered a ``literary work'' under copyright law. The ``literary work'' can be viewed as a sequence of tokens arranged to reflect the author's intentions. Existing MIA techniques\todo{CITE} treat all source code tokens equally and compute membership probabilities of a LLM based on a sample of these tokens. Generally, it is recognized that elements such as variable names, data and control flows, and API usage together with the involved variables, embody the author's intent and serve as indicators of source code authorship. However, we observe that some tokens primarily serve a grammatical purpose, functioning to complete the syntax constraint of the programming language.



\subsection{Syntax Constraints}

We focus on the Python and Java language. To build our syntax pattern database, we combine manual inspection of the official documentation~\cite{python11, javadoc} with automated analysis. For Python, we systematically survey the language specification, focusing on Chapter 8, "Compound statements," which defines the core control flow and organizational structures. This chapter's 10 subsections detail the multi-line constructs rich in syntactic patterns relevant to our work.

Our selection process is grounded in Python's lexical structure. We programmatically retrieve reserved keywords using the \texttt{keyword} module (35 in Python 3.11) to ensure our patterns are based on definitive language elements. Based on this, we analyzed the 10 subsections and included 8 in our database: \texttt{if}, \texttt{for}, \texttt{try}, \texttt{with}, \texttt{match}, function (\texttt{def}) and class (\texttt{class}) definitions, and coroutine (\texttt{async}) structures. These were selected because their syntactic forms are rigid multi-token patterns, identifiable via tokenization, that contain both prefix keywords (e.g., \texttt{for}, \texttt{try}) and structurally determined suffix tokens (e.g., \texttt{in}, \texttt{except}).

We excluded two subsections. The \texttt{while} statement was omitted as its core structure (\texttt{while condition:}) lacks a fixed suffix token. "Type parameter lists" was also excluded as it pertains to type-level declarations, not the executable control-flow syntax central to our study. The syntactic validity of all collected patterns is finally verified using Python's \texttt{ast} module.


The inherent structural duality of source code – simultaneously embodying \textit{human design intent} and \textit{machine-enforced syntax} – introduces unique challenges for membership inference in code language models.

\begin{itemize}
\item \textbf{Syntax-Induced Noise Amplification}: Language-mandated tokens like \texttt{in}, \texttt{except}, and \texttt{:} exhibit near-identical probability distributions across member and non-member samples. Their structural predictability drowns out discriminative signals from author-specific patterns.
\item \textbf{Contextual Ambiguity}: Traditional token-level approaches cannot distinguish between \textit{syntax-enforced occurrences} (e.g., \texttt{in} in \texttt{for x \textbf{in} data}) and \textit{semantically meaningful instances} (e.g., \texttt{if key \textbf{in} dict}). This equivalence creates false attribution pathways.

\end{itemize}

The root challenge stems from code's \textit{mandatory scaffolding} property: any functionally correct implementation must embed programmer intent within grammatical constraints. Whereas natural language allows infinite paraphrasing, code requires specific token sequences to satisfy the interpreter. This creates an adversarial scenario where the very tokens that define correctness (keywords, delimiters) act as persistent noise sources for membership inference.

Our approach leverages the \textit{dual predictability hierarchy} inherent in code:

\textbf{Language-Level Predictability}: Syntax-enforced tokens follow deterministic patterns dictated by Python's grammar

\textbf{Author-Level Predictability}: Unique implementation choices (variable names, API chains) reflect training data memorization

By surgically separating these predictability layers through syntax-aware filtering, we amplify the discriminative power of membership signals while suppressing structural noise. This paradigm shift addresses the core limitation of existing methods – their inability to account for code's machine-enforced regularity – establishing a foundation for code-specific membership inference.


\subsection{Min-k\% Prob with Syntax-Aware Filtering}
We propose \textbf{Syntax-Aware Min-k\% Prob}, an enhanced membership inference method specifically designed for code data. This extension addresses the fundamental difference between natural language and programming languages: code contains \textit{syntax-enforced patterns} where specific token sequences are structurally determined (e.g., \texttt{for...in...}, \texttt{if...else...}). The core insight is that suffix tokens in these patterns (e.g., \texttt{in}, \texttt{else}) exhibit high prediction probabilities regardless of their membership status, introducing noise to the Min-k\% Prob metric. Our method introduces a two-stage filtering process:


\begin{enumerate}
    \item \textbf{Syntax Rule Construction}: 
    Establish a comprehensive syntax rule set $\mathcal{R}$ based on Python's formal grammar specification. For each syntax-bound phrase $r_i \in \mathcal{R}$, we define:
    \[
    r_i = (\phi_{\text{prefix}}, \phi_{\text{suffix}}, \tau)
    \]
    where:
    \begin{itemize}
        \item $\phi_{\text{prefix}}$: Context-sensitive prefix tokens (e.g., \texttt{for}, \texttt{try})
        \item $\phi_{\text{suffix}}$: Structurally determined suffix tokens (e.g., \texttt{in}, \texttt{except})
        \item $\tau$: AST node type for validation (e.g., \texttt{For}, \texttt{Try})
    \end{itemize}
    Our rule set $\mathcal{R}$ covers 23 essential code patterns across 5 categories (control flow, error handling, context management, comprehensions, declarations), rigorously validated against Python 3.11 documentation.

    \item \textbf{Hybrid Pattern Detection}: 
    For input code $x$, perform dual validation:
    \begin{enumerate}
        \item \textit{Surface-Level Matching}: Scan tokens using regular expressions derived from $\phi_{\text{prefix}}$ and $\phi_{\text{suffix}}$
        \item \textit{Semantic Validation}: Construct Abstract Syntax Tree (AST) to verify pattern validity through node type checking with $\tau$
    \end{enumerate}
    This yields verified syntax phrases $\mathcal{P} = \{(p_1^{\text{pre}}, p_1^{\text{suf}}), ..., (p_n^{\text{pre}}, p_n^{\text{suf}})\}$.

    \item \textbf{Context-Preserving Token Filtering}:
    For each detected $(p_i^{\text{pre}}, p_i^{\text{suf}})$: 
    \[
    \mathcal{T}_{\text{filtered}} = \mathcal{T} \setminus \{ t_j \mid t_j \in \bigcup_{i=1}^n p_i^{\text{suf}} \}
    \]
    preserving contextual relationships through:
    % \[
    % \textsc{Keep}(t_k) = \begin{cases} 
    % 0 & \text{if } t_k \in p_i^{\text{suf}} \land \textsc{IsSyntaxEnforced}(p_i^{\text{pre}}) \\
    % 1 & \text{otherwise}
    % \end{cases}
    % \]

    \item \textbf{Adaptive Min-k\% Calculation}:
    Compute membership scores on the filtered token set:
    \[
    \text{Syntax-Min-k\%}(x) = \frac{1}{|\mathcal{S}|} \sum_{t_i \in \mathcal{S}} -\log p(t_i|t_{<i})
    \]
    where $\mathcal{S} = \text{argmin}_{|\mathcal{S}'|=k\%|\mathcal{T}_{\text{filtered}}|} \sum_{t_j \in \mathcal{S}'} p(t_j|t_{<j})$
\end{enumerate}

\begin{tcolorbox}
\textbf{Rationale}: Our dual validation approach ensures \textit{semantic-aware filtering} - we only remove tokens that are both 1) surface-level syntax markers \textit{and} 2) semantically validated by AST structure. For example, the token \texttt{in} is excluded \textit{only} when it appears in a valid \texttt{For} node context, preserving meaningful occurrences in list comprehensions like \texttt{[x for x in y if x \textbf{in} z]}. This focuses the metric on \textit{author-specific patterns} (variable names, API chains) rather than language-mandated syntax.
\end{tcolorbox}
