\subsection{API Compatibility Detection}

The continuous evolution of software libraries inevitably introduces breaking changes, posing severe threats to the stability of downstream applications. In a systematic review, Lamothe et al.\cite{lamothe2021systematic} identified that understanding the specific impacts of API evolution on developers and users remains a paramount challenge. Substantiating this concern, extensive empirical studies have been conducted to characterize the pervasiveness of compatibility issues across diverse ecosystems. In the mobile domain, Cai et al.\cite{cai2019large} conducted a large-scale longitudinal study on Android runtime compatibility, while Liu et al.\cite{liu2022automatically} summarized five categories of API-induced issues. More recently, the focus has deepened into device-specific behaviors~\cite{dong2024same} and compatibility issues caused by vendor customizations~\cite{chen2024demystifying}. Beyond mobile, such challenges are widespread in system software like Linux~\cite{tsai2016study}, compiled languages like Java—where behavioral breaking changes frequently affect client applications~\cite{jayasuriya2024understanding}—and the NPM ecosystem~\cite{kong2025toward}. Even in complex deep learning systems, compatibility issues spanning software and hardware stacks have been rigorously characterized~\cite{wang2023compatibility}. However, distinct from these ecosystems, Python presents unique challenges. Zhang et al.\cite{zhang2020python} revealed that Python framework APIs evolve with patterns significantly different from Java. Recent works have further classified Python-specific incompatibility symptoms\cite{shen2024static} and cross-repository conflicts~\cite{xie2024pet}, underscoring that the dynamic nature of Python makes the compatibility issue more complicated.

A mainstream of the related work apply dynamic techniques. The core strategy of these approaches involves constructing and executing test cases to trigger API behaviors across different versions. For instance, Sun et al.\cite{sun2022mining} proposed JUnitTestGen, which mines real-world API usages to generate executable unit tests. Going a step further to ensure comprehensive coverage, Mahmud et al.\cite{mahmud2024apicia} introduced APICIA, which performs a bidirectional impact analysis. Besides, to address client-specific upgrades, Zhu et al.\cite{zhu2023client} utilized a knowledge-guided framework to generate incompatibility-revealing tests, while Chen et al.\cite{chen2020taming} leveraged cross-project testing to detect behavioral backward incompatibilities in Python. Beyond standard testing, more sophisticated dynamic techniques have been introduced to analyze complex dependency chains. Kong et al.\cite{kong2025more} employed dynamic object relation graphs to precisely detect breaking changes in JavaScript. Furthermore, effective dynamic analysis relies on valid execution environments, a challenge addressed by tools like ReadPyE\cite{cheng2023revisiting} which automates the generation of compatible Python runtimes.

However, the applicability of dynamic analysis is often constrained by its high computational costs and reliance on existing test suites, which can leave parts of the application untested. In contrast, static analysis approaches offer the advantage of analyzing the entire codebase without execution, providing a scalable alternative. In the Android ecosystem, early research progressed along two parallel dimensions: device fragmentation and general API evolution. Addressing fragmentation, Wei et al.\cite{wei2016taming} pioneered FicFinder to characterize device-specific issues, a direction later advanced by Pivot\cite{wei2019pivot} to learn API-device correlations from large corpora. In parallel, to tackle general API evolution, Li et al.\cite{li2018cid} introduced CiD to model API lifecycles, while He et al.\cite{he2018understanding} developed IctApiFinder to detect incompatible usages. As the field matured, techniques evolved towards automated repair and finer granularity. Xia et al.\cite{xia2020android} designed RAPID to mine repair templates from application history. Concurrently, detection depth increased significantly: from general methods to complex callbacks (ACID\cite{mahmud2022acid}, Huang et al.\cite{huang2018understanding}) and field-level evolutions (FCID\cite{mahmud2024empirical}, AndroMevol~\cite{liu2023automatically}), with recent work identifying recurring design smells~\cite{jin2025design}. Beyond Android, static techniques have advanced in other domains. In Java, tools like APIDiff~\cite{brito2018apidiff} and the recent source-based Roseau~\cite{latappy2025roseau} focus on identifying breaking changes. In the Python domain, static analysis has been tailored to its specific ecosystem. Zhang et al.\cite{zhang2020python} developed PyCompat to handle framework API evolution, while Zhao et al.\cite{zhao2023knowledge} constructed knowledge bases to detect version incompatibilities in deep learning stacks. Other tools target specific risks such as breaking changes in packages (Aexpy~\cite{du2022aexpy}), deprecated APIs (APIScanner~\cite{vadlamani2021apiscanner}), and complex variadic parameters~\cite{zhang2024coding}. More recently, static approaches have expanded to classify Python incompatibility types~\cite{shen2024static} and solve cross-repository issues via offline database construction~\cite{xie2024pet}.

Despite the advancements in static analysis, these approaches encounter severe bottlenecks when applied to dynamic languages. Python's dynamic features, such as runtime type inference and dynamic attribute access, often evade capture by rigid control-flow or data-flow analysis, resulting in high false positive rates or missed subtle semantic changes. To bridge these gaps, our work integrate LLMs, enhanced via Chain-of-Thought (CoT) reasoning and multi-agent collaboration. This approach capitalizes on LLMs' ability to interpret implicit API behaviors, infer context-dependent compatibility rules, and adapt to diverse usage scenarios—capabilities that resolve the semantic detection limitations of all preceding traditional static methods.

\subsection{LLMs for Library Evolution}

With the rapid advancement of Large Language Models (LLMs), researchers have actively explored their potential in automating complex tasks within the domain of library evolution, leveraging their semantic understanding.

Researchers have applied LLMs to address various challenges in library evolution, primarily focusing on two distinct tasks: managing deprecated APIs and adapting code generation. For Deprecated API management, Mahmud et al.\cite{mahmud2024automated} proposed GUPPY, the first LLM-based approach to automatically update Android deprecated API usages without requiring manual templates. Similarly, to prevent the introduction of outdated APIs during generation, Bai et al.\cite{bai2024apilot} developed APILOT, which leverages real-time differential analysis to verify LLM outputs against a database of outdated APIs. Regarding API Usage Adaptation and robust code generation, Li et al.~\cite{li2025structured} introduced Structured Chain-of-Thought (SCoT). By incorporating programming structures (sequence, branch, loop) into intermediate reasoning steps, SCoT aims to solve the low accuracy of LLMs in generating complex, structurally correct code that adapts to specific requirements.

To enhance the performance of LLMs in various tasks, advanced prompting and architectural techniques have been employed. Chain-of-Thought (CoT), originally proposed by Wei et al.\cite{wei2022chain} to elicit reasoning, has evolved significantly. Zhang et al.\cite{zhang2025enhancing} enhanced CoT by constructing task-specific reasoning patterns. In the specific domain of code synthesis, Li et al.~\cite{li2025structured} further advanced this by proposing Structured CoT (SCoT), which explicitly embeds programming logic (e.g., branches and loops) into the reasoning chain to constrain the model's output. Meanwhile, Liu et al.\cite{liu2024era} proposed ERA-CoT to capture entity relationships for better context understanding. Agent-based system is another outstanding architectural technique. Ma et al.\cite{ma2024combining} proposed iAudit, a multi-agent framework combining a Ranker and Critic to debate vulnerabilities in smart contracts. Similarly, Sun et al.\cite{sun2024gptscan} developed GPTScan, which combines GPT's capability in recognizing key variables with static program analysis to detect logic vulnerabilities.

Despite these advancements, fundamental challenges persist in applying LLMs to library evolution. Wang et al.\cite{wang2024llms} quantitatively revealed that LLMs frequently utilize deprecated APIs due to outdated training data. Liang et al.\cite{liang2025rustevo} further confirmed that the knowledge cutoff significantly hampers performance , although Retrieval-Augmented Generation (RAG) can mitigate this. Critically, existing solutions leave a methodological gap: current CoT approaches and multi-agent frameworks lack design for API compatibility issues. To address these limitations, our work introduces a specialized multi-agent framework. We design a CoT prompt mechanism to explicitly reason about incompatibility categories and orchestrate Input-Generator and Simulater agents to construct a closed-loop verification system.
