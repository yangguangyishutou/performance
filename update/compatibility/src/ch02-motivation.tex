\subsection{Python Incompatibilities in the Wild}

We focus on incompatible APIs in Python, a widely used language whose issues are representative of modern software ecosystems. The incompatible APIs involve the interaction between the upstream dependencies and the downstream client usages. Given an API evolves from an older version to a newer version, the \textit{forward incompatibility} occurs when the newer version introduces changes that prevent existing client code from running correctly, and the \textit{backward incompatibility} occurs when code written for the newer version cannot run correctly on the older version. The incompatible APIs can introduce substantial development overhead and may result in production failures or service disruptions.

To understand the prevalence and severity of these issues, we perform a lightweight empirical study on Python API incompatibilities in the wild. Specifically, we selected 53 popular projects from GitHub, such as \texttt{urllib3}, \texttt{aioboto3}, and \texttt{flask}. We initially harvested 8,167 issues using keywords related to compatibility and exceptions (e.g., 'version', 'TypeError', 'AttributeError', 'evolution', 'exception'). To ensure data quality, we applied a multi-stage filtering process. First, we filtered out general bug reports, fixes, and issues with incomplete descriptions, reducing the dataset to 2,480 candidates. Next, to focus on code-level incompatibilities, we retained 1,460 issues that were explicitly related to dependency logic rather than environment misconfigurations. Subsequently, we screened the issues based on the completeness of versioning and function information. Finally, we performed a manual verification on the remaining candidates to filter out false positives, yielding 68 confirmed incompatibility issues.

These collected issues reveal a recurring pattern where developers struggle with unexpected breaking changes triggered by third-party library updates. A representative case is found in \texttt{aiobotocore} issue #52\footnote{https://github.com/aio-libs/aiobotocore/issues/52}, where the upstream dependency \texttt{botocore} introduced a new parameter to an internal function. This change caused a mismatch in the downstream usage, resulting in a runtime crash: \texttt{TypeError: \_get\_clien\_args() takes 9 positional arguments but 10 were given}. The discussion in this issue highlights the significant overhead and frustration caused by such instability. One developer complained that the upstream library makes frequent changes that break aiobotocore, forcing them to manually downgrade the package to restore functionality. The project maintainer acknowledged that their library relies on internal interfaces that change often, and ultimately decided to pin version of botocore as a desperate workaround.

As the above case illustrates, resolving such incompatibility issues requires deep semantic analysis of variable types and execution paths. These subtle changes are often difficult to detect through traditional static analysis alone. Fortunately, Large Language Models (LLMs) possess the semantic understanding capabilities necessary to bridge this gap, enabling more accurate detection of complex API incompatibilities.

\subsection{Categories of Compatibility Types}





\begin{itemize}
    \item {\textbf{CI1}: The function parameter is either deleted in the \texttt{API}$_{before}$ or added in the \texttt{API}$_{after}$. As shown in Fig.1, \texttt{amount} is required in \texttt{API}$_{before}$ but removed in \texttt{API}$_{after}$. Calling \texttt{API}$_{after}$(amount=1) will raise a \texttt{TypeError}: "fun() got an unexpected keyword argument 'amount'.}
    \item {\textbf{CI2}: Both versions have '$**kwargs$', but different keys exist in the \texttt{API}$_{before}$ and \texttt{API}$_{after}$. As shown in Fig.1, \texttt{API}$_{before}$ extracts the key \texttt{'key'} from \texttt{**kwargs}, while \texttt{API}$_{after}$ extracts \texttt{'key\_for\_check'}. If the client supplies only an object with a \texttt{get} method, calling \texttt{API}$_{after}$ may raise a \texttt{KeyError}: \texttt{key\_for\_check}.}
    \item {\textbf{CI3}: The function parameter from \texttt{API}$_{before}$ is renamed in the \texttt{API}$_{after}$. As shown in Fig.1, \texttt{n\_size} in \texttt{API}$_{before}$ is renamed to \texttt{n\_dim} in \texttt{API}$_{after}$. Calling \texttt{API}$_{after}$(n\_size=...) will therefore raise a \texttt{TypeError}: "fun() got an unexpected keyword argument 'n\_size'".}
    \item {\textbf{CI4}: The default value of a parameter from \texttt{API}$_{before}$ is changed into another value in \texttt{API}$_{after}$. As shown in Fig.1, the default of \texttt{flag} changes from \texttt{True} in \texttt{API}$_{before}$ to \texttt{False} in \texttt{API}$_{after}$. Thus, invoking the API without specifying \texttt{flag} can follow a different execution path and produce different results (e.g. \texttt{API}$_{before}$ may return \texttt{False} early, while \texttt{API}$_{after}$ may skip that branch and return \texttt{new\_var(list)}).}
    \item {\textbf{CI5}: The boundary values of parameters change. As shown in Fig.1, the condition that triggers a \texttt{TypeError} changes from \texttt{kwargs.get('key')} in \texttt{API}$_{before}$ to \texttt{kwargs.get('key\_for\_check') and self.type\_bad()} in \texttt{API}$_{after}$. Consequently, the same \texttt{kwargs} object may cause an error in one version but not the other.}
    \item {\textbf{CI6}: The \texttt{API}$_{before}$ or \texttt{API}$_{after}$ contain unique exceptions under the condition that the other one does not have. As shown in Fig.1, when \texttt{len(new\_val)} holds, \texttt{API}$_{before}$ raises a \texttt{ValueError} whereas \texttt{API}$_{after}$ raises a \texttt{LENError}.}
    \item {\textbf{CI7}: The returned value changes given the same API input. As noted in CI4, changing a default can cause the API to return different values for the same call (e.g. \texttt{False} in \texttt{API}$_{before}$ vs. \texttt{new\_var(list)} in \texttt{API}$_{after}$.}
    \item {\textbf{CI8}: The global value changes given the same API input. As shown in Fig.1, there is a global variable 'GLOBALX' used in both \texttt{API}$_{before}$ and \texttt{API}$_{after}$. when \texttt{flag} is \texttt{True}, \texttt{API}$_{before}$ assigns \texttt{GLOBALX = n\_size}, while \texttt{API}$_{after}$ assigns \texttt{GLOBALX = n\_dim} or \texttt{None}.}
    \item {\textbf{CI9}: The value for reference parameter (e.g., 'self') changes given the same API input. As shown in Fig.1, \texttt{API}$_{before}$ sets \texttt{self.amount = amount}, whereas \texttt{API}$_{after}$ does not set \texttt{self.dimension}; thus the object's attributes after the call may differ between versions.}
\end{itemize}
