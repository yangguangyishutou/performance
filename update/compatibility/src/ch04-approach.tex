\subsection{Challenges and Design Motivation}


Existing static analysis methods (e.g., Shen et al.~\cite{shen2024static}) rely on handcrafted rules. However, rule design requires substantial expert knowledge, making such approaches difficult to generalize to new libraries or previously unseen incompatibilities. Moreover, rule-based methods fail to capture semantic context. For example, when a parameter is renamed from \texttt{arguments} to \texttt{args}, the corresponding AST patterns differ syntactically. As a result, rule-based approaches cannot recognize the underlying rename operation.

Having witnessed the effectiveness of large language models (LLMs) in software engineering tasks\todo{CITE}, we naturally think of the opportunities of leveraging LLMs to detect incompatible Python APIs. However, recognizing their limitations and to fully harness their potential, we identify the following three challenges in its practical application.

\begin{itemize}
    \item \textbf{I. Linking incompatibility category description to specific code changes.} Each incompatibility category begins with a brief description of how it manifests. However, when such descriptions are provided directly to an LLM, it may fail to fully infer their correspondence to specific code changes. This misalignment between natural-language descriptions and syntactic code changes creates a gap that can hinder the model's effectiveness.
    \item \textbf{II. Scalability with categories of incompatibilities.} Each incompatibility category exhibits distinct syntactic characteristics. A natural approach is to design a dedicated instruction for the LLM for each category. However, as the number of incompatibility categories grows, this approach would require repeated API scanning and reasoning, leading to excessive token consumption and longer execution times, ultimately rendering it impractical for large-scale analyses.
    \item \textbf{III. LLM hallucination and unreliability.} The LLM may generate hallucinated content and exhibit low confidence in its responses. As a result, some outputs may contain false, contradictory, or inconsistent claims. e.g., citing non-existent code lines to support an assertion.
\end{itemize}



To address Challenges \textbf{I} and \textbf{III}, the LLM should fully comprehend the causes of incompatibility from the perspective of code changes and their underlying logic across versions. This requires the LLM to analyze code in a manner similar to a static analyzer, while additionally capturing semantic intent. To tackle Challenge \textbf{II}, the LLM should examine the code statements of both versions sequentially from top to bottom and produce intermediate analysis results for each statement. These intermediate states can then be aggregated to determine the final incompatibility category upon completion of the analysis. Furthermore, to mitigate hallucination and unreliability, additional reflection mechanisms are required to validate the LLM's analysis.

Guided by these requirements, we propose decomposing the reasoning process for incompatibility classification into fine-grained steps. The LLM incrementally computes intermediate states while analyzing each statement and integrates them into a unified, structured reasoning framework, thereby addressing Challenges I and II. In addition, we incorporate a self-reflection phase in which the LLM validates its static analysis results from the perspective of test-case behavior.

\subsection{Static Oriented Reasoning}\label{subsec:static_reasoning}

This section details our static analysis framework. Unlike traditional compiler-level approaches, we employ a lightweight, semantic abstraction designed to efficiently detect behavioral incompatibilities between API versions.

\subsubsection{Control Flow Graph Construction}\label{subsubsec:cfg_construction}

The emphasis of our approach is not on classical compiler-level Control Flow Graphs (CFGs), but on a deliberately lightweight, semantic abstraction sufficient for detecting behavioral incompatibilities. At a conceptual level, our CFG is a \textbf{condition-indexed execution context graph}, where nodes represent semantic events (assignments, exceptions, returns) and edges are implicit, encoded via condition scope indices rather than explicit jumps. This design implies that explicit control edges, such as jump targets and loops, are unnecessary for CI detection.

The foundation of the CFG is the set of condition statements, denoted as $C$. Each element in $C$ corresponds to a syntactic condition encountered during the scan of the function body, including \texttt{if}, \texttt{elif}, \texttt{else}, \texttt{while}, and exception-handling constructs. Conditions are stored as normalized strings and assigned monotonically increasing indices. These indices serve as stable identifiers for control contexts and function as decision nodes in the implicit CFG. To track the currently active execution context, the construction process maintains a condition stack, $CS$, while scanning the source code. This stack is updated in a single top-down scan: when the analysis enters a new conditional scope, the corresponding condition index is pushed onto the stack; when the scope ends, it is popped.

Data flow information is captured in the structure $D$, which represents the primary computational nodes of the CFG. Each entry in $D$ corresponds to an assignment statement and records four elements: $(var, var\_type, dependencies, condition\_indices)$. In CFG terms, each such entry is a statement node whose control dependencies are fully described by its associated condition indices (a snapshot of $CS$). Explicit control-flow edges are therefore unnecessary, as all relevant control information is encoded in this metadata.

Terminal behaviors of the function are represented by the exception set $E$ and the return set $R$. Each explicit exception statement—limited strictly to \texttt{raise} and \texttt{assert} constructs—is recorded in $E$ along with the active condition indices. Similarly, each \texttt{return} or \texttt{yield} statement is recorded in $R$ with its guarding conditions. Implicit behaviors, such as falling off the end of a function or logging-based warnings, are intentionally excluded because they do not reliably affect API contracts.

The entire CFG is constructed in a single pass over the function body (Algorithm \ref{alg:cfg_construction}). This one-pass design is a critical property. Because the analysis does not require successor resolution, loop unrolling, or interprocedural reasoning, all necessary control and data dependencies can be captured incrementally. Upon encountering a condition, it is registered and pushed onto the condition stack. Upon encountering an assignment, exception, or return, a node is created with a snapshot of the current stack.

An important aspect of the construction process is its deliberate selectivity. Only entities that are relevant to API-level incompatibility are recorded. Conditions are retained only insofar as they guard observable behaviors. Data flows are recorded only for assignments that may affect return values, exceptions, global state, or reference parameters. Conversely, many elements commonly present in full CFGs are intentionally ignored, including call graphs, logging statements, exception messages, loop iteration counts, and internal refactoring that does not affect externally visible behavior. This pruning is essential for maintaining robustness when the analysis is performed by an LLM.

\subsubsection{Source-Sink Labeling}

At a high level, source-sink labeling assigns semantic roles to selected program entities so that data-flow paths relevant to API contracts can be isolated and compared across versions. The key idea is that not all variables are equally important for API compatibility. Only entities that represent externally observable inputs, externally observable outputs, or persistent side effects are labeled. All other intermediate computations are treated as unlabeled internal glue.

\paragraph{Sources} 
Sources correspond to entities that introduce data into the function from the caller or the external environment. The primary sources are function parameters extracted in Phase 1, including positional parameters, optional parameters with defaults, and \texttt{**kwargs}. They define the input surface of the API. Type annotations are explicitly ignored, reinforcing that labeling is driven by runtime semantics. Within parameters, \textbf{\texttt{**kwargs}} receives special treatment. The object itself is labeled as a source, but more importantly, individual keys accessed via \texttt{kwargs.get('key')} or \texttt{kwargs['key']} are labeled as distinct fine-grained sources. This reflects the fact that keys effectively behave as optional named parameters. Keys are only labeled when they are explicitly accessed in the function body; keys that are never read are ignored to prevent over-approximation. Additionally, renamed parameters identified in the \textit{ReName} structure are implicitly treated as corresponding sources across versions. The \textit{ReNUsage} mapping provides the evidence to align these labels, distinguishing true renames from unrelated changes.

\paragraph{Sinks} 
Sinks represent points where data influences externally observable behavior. The most prominent sinks are \textbf{return statements}. Each return expression is labeled as a sink because it directly determines the value observed by the caller. Importantly, return sinks are condition-sensitive: a return expression is associated with the set of active condition indices under which it executes. \textbf{Explicit exception statements} form another critical class of sinks. Each \texttt{raise} or \texttt{assert} statement is labeled as a sink because exceptions alter the control flow visible to callers. The label records the exception type and the guarding conditions, while exception messages are intentionally excluded. Beyond direct outputs, certain \textbf{side effects} are labeled as sinks. Assignments to global variables are labeled because they may affect program state beyond the function boundary. Similarly, assignments to reference parameters (e.g., \texttt{self} or mutable objects) are labeled when they modify the reference itself or its attributes.

The labeling process is tightly integrated with the one-pass scan used for CFG construction. When a labeled source is introduced, it is recorded once and referenced symbolically. When a labeled sink is encountered, it is recorded together with the current condition stack. Data-flow entries in $D$ act as the connective tissue between sources and sinks. Local variables that neither originate from labeled sources nor contribute to labeled sinks are left unlabeled, reducing noise for LLM-based reasoning.

\subsubsection{Graph Traversing}

The graphs produced in earlier phases are implicit rather than explicitly materialized. Control flow is encoded via condition indices, and data flow is encoded through dependency lists in the $D$ structure. As a result, graph traversal does not involve explicit edge-following but is realized as structured queries over node sets, guided by labels, dependencies, and control conditions.

Traversal always begins from semantically meaningful anchor points rather than arbitrary nodes. These anchors include labeled sources (parameters, kwargs keys) and labeled sinks (returns, exceptions, side effects). By restricting traversal origins to these anchors, the analysis avoids unnecessary exploration of internal implementation details. Control sensitivity during traversal is achieved through condition indices rather than explicit branching. When traversing from or to a node, its associated list of condition indices is treated as a path predicate. Two nodes are considered control-aligned if their condition index sets are equivalent or comparable. This allows traversal to reason about execution contexts without constructing explicit true or false edges.

Data-flow traversal is primarily backward and dependency-driven. Starting from a sink node, such as a return statement, traversal proceeds backward through the $D$ structure by following dependency relationships. If a return expression depends on variable $v$, traversal identifies assignments to $v$ and recursively inspects the variables on which those assignments depend. Traversal is deliberately bounded. It does not compute full transitive closures but stops as soon as one of three conditions is met: a labeled source is reached, a dependency chain diverges structurally between versions, or the remaining dependencies are deemed semantically irrelevant.

Traversal operates in a comparative mode for version alignment. Traversal over the graph of \textit{code\_v1} is paired with traversal over \textit{code\_v2}. Nodes are aligned based on labels, variable roles, and control contexts. Differences in control flow that do not guard labeled sinks (e.g., refactoring of internal loops) are ignored to maintain a high signal-to-noise ratio.

\subsubsection{Incompatibility Analysis}

The analysis phase assumes that control-flow and data-flow information has already been selectively traversed and aligned across versions. It reasons over the extracted information to determine whether specific compatibility rules are violated.

\paragraph{Signature-Level Incompatibilities}
These are resolved entirely outside the graph to prevent spurious interactions. This includes \textbf{parameter addition/deletion (CI1)} and \textbf{default value changes (CI4)}, which are detected through direct comparison of parameter lists.

\paragraph{Body-Level Incompatibilities}
Using the traversed graph information, we apply deterministic rules to detect the following:

\begin{itemize}
    \item \textbf{Kwargs Incompatibility (CI2):} The analysis compares the sets of explicitly accessed kwargs keys ($K1$ and $K2$) identified during traversal. A mismatch indicates a change in the effective input surface. Since unused keys are filtered out, this directly reflects behavioral differences.
    \item \textbf{Parameter Rename Incompatibility (CI3):} We evaluate whether pairs of renamed parameters (from \textit{ReName}) have structurally equivalent data-flow subgraphs. If the extracted subgraphs differ only in variable names but preserve the roles in computations and conditions, it is a valid rename; otherwise, it is an incompatibility.
    \item \textbf{Range Incompatibility (CI5):} The analysis inspects whether parameter-controlled conditions lead to different exception behaviors across versions. This relies on comparing exception nodes together with the identified guarding conditions.
    \item \textbf{Exception Incompatibility (CI6):} This covers differences in exception types, the addition/removal of exception statements, or exception behavior under non-input-related conditions. Separating CI5 and CI6 ensures that range changes and general type changes are not conflated.
    \item \textbf{Return Value Incompatibility (CI7):} We compare aligned return nodes and their data-flow slices. If a return expression in one version has no counterpart in the other, or if upstream data flows produce different values, an incompatibility is reported.
    \item \textbf{Global Variable Incompatibility (CI8):} Differences in the presence of global-variable assignments or their dependency structures indicate potential changes to externally visible shared state.
    \item \textbf{Reference Parameter Incompatibility (CI9):} The analysis inspects assignments to reference parameters and their attributes, focusing strictly on state mutations rather than access patterns.
\end{itemize}

Across all types, the analysis applies these rules deterministically to the traversed graph information, ensuring that each reported incompatibility is accompanied by a concise, structurally grounded reason.


\subsection{Dynamic Simulated Reflection}


To address judgment biases in the incompatibility category candidates generated by the CoT-LLM, we design a multi-agent collaborative validation framework. It implements accurate verification of candidate categories through a process of "test case generation, simulation execution, and comprehensive evaluation," ultimately filtering out truly valid API incompatibility types. The framework comprises three functionally independent yet collaboratively working agent modules: the Test Case Generation Agent, Simulation Agent, and Comprehensive Analysis Agent. These modules form a validation chain through explicit information interaction, ensuring the objectivity and reliability of validation results.

\subsubsection{Test Case Generation}

The Test Case Generation Agent serves as the initiator of the validation process, tasked with constructing targeted test inputs to probe potential incompatibilities. Its core functionality is to generate pairs of calling statements—one for the old API version and one for the new—along with supplementary context, based on the provided old and new API code snippets, the candidate incompatibility category, and the underlying reasoning. The design of these test cases adheres to a critical principle: they must be highly likely to trigger the alleged incompatibility if it indeed exists. For instance, when evaluating a candidate issue related to changed default parameter values, the agent will craft calling statements that omit the affected parameters, thereby exposing discrepancies in behavior caused by the default value shift. The output of this agent follows a structured format, explicitly separating the calling statements and supplementary information for the old and new APIs to ensure clarity in subsequent processing.

The collaborative workflow of the three agents forms a closed-loop validation pipeline. Starting with a candidate incompatibility category, the Test Case Generation Agent tailors probes to expose potential issues, the Simulation Agent generates empirical behavioral data, and the Comprehensive Analysis Agent renders a data-driven judgment. This division of labor ensures that each stage of validation is handled by a specialized component, reducing the risk of subjective biases that might arise from a single model’s judgment. By structuring the validation as an explicit information flow—from test design to execution to analysis—the framework enhances the transparency and reproducibility of the verification process. Ultimately, this multi-agent approach strengthens the reliability of incompatibility category identification, providing a robust mechanism to filter out spurious candidates and retain only those that are empirically validated.

\subsubsection{Step-by-step Simulation}

Upon receiving the test cases from the Test Case Generation Agent, the Simulation Agent takes on the role of executing these tests in a controlled environment. Its primary responsibility is to simulate the runtime behavior of both the old and new API versions when invoked with the generated test inputs. This involves parsing the API code, instantiating necessary objects (if applicable), and executing the calling statements step-by-step. The agent meticulously records the execution results: if the program exits normally with a return value, it captures the specific output; if an exception is raised (e.g., missing arguments, type errors), it documents the error type and description. By faithfully replicating runtime scenarios, this agent transforms abstract code differences into concrete behavioral outcomes, providing empirical data for validating the alleged incompatibility.


\subsubsection{Simulated Result Analysis}

The Comprehensive Analysis Agent acts as the final evaluator, synthesizing information from the preceding stages to assess the validity of the candidate incompatibility category. It takes as input the definition of the incompatibility type, the reasoning behind the initial diagnosis, and the behavioral results generated by the Simulation Agent. Using a scoring mechanism ranging from 0 to 10, the agent evaluates the alignment between the diagnosed incompatibility, the test case design, and the observed runtime behaviors. The score is determined based on three key criteria: logical consistency (whether the reasoning logically leads to the alleged incompatibility), rigor of evidence (whether the simulation results clearly demonstrate the expected behavioral discrepancy), and coherence (whether all components of the validation process reinforce the same conclusion). A higher score indicates greater confidence in the existence of the specific incompatibility, while a lower score suggests either flaws in the initial diagnosis or inadequacies in the test scenario.
