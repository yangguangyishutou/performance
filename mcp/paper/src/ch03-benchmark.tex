\subsection{Benchmark Construction}

To construct our benchmark, we apply a five-step process. The containing samples are of the Python language, which is the dominant language in the current MCP ecosystem (95\% of the ecosystem share)~\cite{hasan2025model}.

\textbf{(1) Vulnerability Type Collection.} To understand the prevalent vulnerability types in existing MCP-based systems, we analyzed publicly disclosed vulnerabilities in the National Vulnerability Database (NVD)~\cite{nist_nvd}. Using the keyword ``MCP'', we identified 34 vulnerable MCP servers. Our analysis reveals four dominant vulnerability categories: remote code execution (RCE), denial of service (DoS), SQL injection (SQLi), and insecure file operations (IFO). In addition, we reference the OWASP OWASP LLM Top 10~\cite{owasptop10} to complement our classification. Given that MCP servers typically have access to sensitive data and external resources, we additionally include sensitive information disclosure (SID) as a relevant risk category. The remaining nine risk types in the OWASP LLM Top 10 are excluded, as they are not directly applicable to MCP server architectures.


\textbf{(2) Vulnerability-Triggering Expression Collection.} We collect vulnerability-triggering expressions (e.g., function calls) corresponding to the five identified vulnerability types.


\begin{itemize}[leftmargin=*]

    \item \textbf{Remote Code Execution (RCE).} We construct RCE vulnerabilities by introducing unsafe system shell invocations and dynamic code evaluation calls into the MCP codebase. For system shell invocation, we select calls including \texttt{os.system()}, \texttt{subprocess.run(shell=True)}, \texttt{subprocess.call()}, and \texttt{asyncio.} \texttt{create\_subprocess\_shell()} with unsanitized user input, thereby enabling direct shell command injection. In addition, we incorporate the use of ctypes to invoke the underlying \texttt{libc.system()} function, further expanding the attack surface at the native C++ library layer. For dynamic code execution, we introduce calls to \texttt{exec()}, \texttt{eval()}, \texttt{timeit.timeit()}, and \texttt{runpy.run\_path()} to construct scenarios that permit arbitrary Python code execution. Furthermore, we include expression evaluation through \texttt{pandas.query()}, which can also lead to code injection if improperly handled.

    \item \textbf{Sensitive Information Disclosure (SID).} We construct scenarios in which MCP servers may access and expose sensitive information from external data sources. Specifically, we simulate cases involving the retrieval of email contents (i.e., the MCP tool directly feeds unsanitized email content into the LLM's context through a return statement) and log files, as well as the copying of sensitive data from private locations to publicly accessible directories (\texttt{shutil.copy()}).

    \item \textbf{Insecure File Operation (IFO).} Insecure file operations (IFO) include path traversal and improper file permission management. For path traversal, we construct attacks using the unfiltered \texttt{open()} function with \texttt{../} sequences or URL-encoded patterns to bypass directory constraints. We also exploit path-overwriting in \texttt{os.path.join()} for absolute paths, resolution inconsistencies in \texttt{pathlib.Path()}, and unintended file enumeration via wildcards in \texttt{glob.glob()}. Improper file permissions include unauthorized deletion (\texttt{os.remove()}, \texttt{shutil.rmtree()}), insecure permission changes (\texttt{os.chmod()}), arbitrary reading (\texttt{linecache.getline()}), unrestricted symlink traversal (\texttt{os.walk()}), and TOCTOU race conditions between link validation (\texttt{os.path.i} \texttt{slink()}) and subsequent file access (\texttt{open()}).

    \item \textbf{SQL Injection.} We include the standard \texttt{execute()} call, the primary query interface for major relational databases (e.g., MySQL, PostgreSQL, SQLite, and Microsoft SQL Server). We further extend our coverage to widely used ORM and data-access frameworks, including SQLAlchemy's raw SQL interface \texttt{sqlalchemy} \texttt{.text()}, Pandas' direct query execution via \texttt{pandas.read\_sql()}, MongoDB's \texttt{find()} operation, and Redis Lua script evaluation through \texttt{redis.eval()}.

    
    \item \textbf{Denial of Service (DoS).} DoS attacks target computational (CPU), memory, and storage resources. For CPU exhaustion, we model vulnerable regular expressions (e.g., \texttt{re.match()}, \texttt{re.comp} \texttt{ile()}) prone to ReDoS, and unbounded computations such as \texttt{math.fact} \texttt{orial()} or deep recursion without input limits, causing potential stack overflows. Memory exhaustion includes reading an expanded ZIP bomb (\texttt{zipfile.ZipFile.read()}) and unconstrained string multiplications. Disk exhaustion is simulated via file descriptor leaks (repeated \texttt{open()} without \texttt{close()}) and uncontrolled \texttt{f.write()} operations. At the business logic level, we model infinite loops, including non-terminating pagination (returning a new \texttt{uuid.uuid4()} as \texttt{next\_page\_token}), endlessly expanding directory trees, and circular authentication deadlocks.

For memory exhaustion, we include cases such as reading the full contents of an expanded ZIP bomb via \texttt{zipfile.ZipFile.read()} and performing unconstrained string multiplications that trigger excessive memory allocation. \textbf{(3) Varying Context Generation.} We apply multiple varying contexts surrounding the vulnerability-triggering expressions to ensure the robustness and generalization ability of the dataset in complex real-world scenarios. 

\begin{itemize}[leftmargin=*]
    \item \textbf{Encoding Variants.} We incorporate multiple encoding techniques to evaluate detector robustness. Specifically, we apply hexadecimal (Hex) and Base64 encodings, which are commonly used to represent binary data in text-based formats and to standardize cryptographic hash outputs. These transformations allow us to assess whether detectors can correctly identify semantically equivalent vulnerabilities expressed in encoded variants.
    
    \item \textbf{Dynamic Invocation.} We employ Python reflection to dynamically resolve and invoke system functions, such as constructing system call references through \texttt{getattr()}, thereby obscuring direct API usage.
 
    \item \textbf{Incomplete defenses.} We construct samples with incomplete defenses to mimic common developer biases. For RCE and SQLi, MCP servers use fragile single-pass blacklist sanitization (e.g., \texttt{replace()} without recursion), failing against double-write nesting or mixed-case obfuscation. For insecure file operations, URL-decoded inputs undergo single-pass traversal removal (e.g., \texttt{unquote()} + \texttt{replace(../'', ’’)}) and imprecise \texttt{startswith()} checks on non-normalized paths, ignoring canonicalization issues. Finally, covert fallback vulnerabilities occur when strict checks (e.g., \texttt{int()} conversion) fail, and the server reverts to unsafe operations like f-string SQL queries.

For RCE and SQLi, MCP servers adopt a fragile single-pass blacklist sanitization strategy (e.g., invoking \texttt{replace()} once without recursive processing), which fails to block keywords crafted through double-write nesting or mixed-case obfuscation. For insecure file operations, we model flawed path sanitization mechanisms in which URL-decoded inputs undergo only a single-pass removal of traversal patterns (e.g., applying \texttt{unquote()} followed by a single \texttt{replace("../", "")}), as well as imprecise prefix validation that relies on \texttt{startswith()} over joined but non-normalized paths. These implementations fail to account for canonicalization inconsistencies and path equivalence issues. Finally, we simulate covert fallback vulnerabilities, where the MCP server reverts to unsafe operations when secure mechanisms fail. For example, upon a \texttt{ValueError} triggered by strict type casting (e.g., \texttt{int()} conversion), the system falls back to string-based SQL query construction (e.g., f-strings), thereby reintroducing injection risks.

    
\end{itemize}

Specifically, it dynamically instantiates predefined vulnerability categories, trigger logic, and variant techniques to produce diverse yet controlled risk scenarios. \textbf{(5) Vulnerable MCP Server Fixing.} We fix MCP vulnerabilities by type. For RCE, we remove user-controlled execution flows, replacing shell-based APIs (e.g., \texttt{os.system()}) with parameterized subprocess calls (\texttt{shell=False}) and substituting dynamic execution primitives (e.g., \texttt{exec()}, \texttt{eval()}) with predefined dispatch logic. Unsafe deserialization (e.g., \texttt{pickle}) is replaced with data-only formats (e.g., JSON), and strict input validation with canonicalization confines external data. For sensitive information disclosure, we enforce separation between data and instructions via structured JSON, role-label sanitization, parameter whitelists, and bounded outputs. Insecure File Operations are mitigated with a “normalize-then-validate” sandboxing: paths are canonicalized (\texttt{abspath()}, \texttt{resolve()}) and checked against a base directory, with symlink validation, multi-pass decoding, and secure temporary file APIs. For DoS, we enforce deterministic limits on recursion, iteration, memory, and decompression, optimize regex patterns against ReDoS, use non-blocking asynchronous execution, and set explicit termination conditions to prevent infinite loops. SQLi is prevented via parameterized queries, whitelisted identifiers, strict type validation, and elimination of unsafe fallback logic, ensuring data is isolated from executable commands.

\textbf{Manual Validation.} Two authors independently conducted a cross-validation and identified 10 erroneous entries out of the 150 implementations. Four vulnerable entries were found unexploitable in practice. We revised their logic to ensure exploitability. The remaining six vulnerability-fixed entries contained flawed patches, either due to overly strict sanitization that broke functionality or incomplete mitigations still bypassable. These patches were refined accordingly. All revised entries then underwent a second independent review until both authors unanimously confirmed their correctness.

\subsection{Metrics}


\textbf{Precision and Recall.} Precision evaluates the proportion of true vulnerabilities among those identified by the model. Recall reflects the proportion of correctly detected vulnerabilities among all ground-truth vulnerabilities. F1-score measures the harmonic mean of precision and recall, providing a balanced assessment of the model's detection performance.


\textbf{Matched Pair Accuracy.} Traditional precision and recall metrics cannot fully capture whether the model genuinely distinguishes between positive and negative samples based on underlying code semantics, or merely relies on superficial matching of specific API calls. Leveraging our paired benchmark, where each vulnerable sample is matched with its fixed counterpart, we employ Matched Pair Accuracy (MPA)~\cite{matchedpair}. A pair is deemed correct only when both instances are classified correctly. MPA thus captures the proportion of pairs for which the model simultaneously identifies the vulnerable and non-vulnerable samples correctly.
