\textbf{(1) Vulnerability Type Collection.} To understand the prevalent vulnerability types in existing MCP-based systems, we analyzed publicly disclosed vulnerabilities in the National Vulnerability Database (NVD)~\cite{nist_nvd}. Using the keyword ``MCP'', we identified 34 vulnerable MCP servers. Our analysis reveals four dominant vulnerability categories: remote code execution (RCE), denial of service (DoS), SQL injection (SQLi), and insecure file operations (IFO). In addition, we reference the OWASP OWASP LLM Top 10~\cite{owasptop10} to complement our classification. Given that MCP servers typically have access to sensitive data and external resources, we additionally include sensitive information disclosure (SID) as a relevant risk category. The remaining nine risk types in the OWASP LLM Top 10 are excluded, as they are not directly applicable to MCP server architectures.

The primary purpose of constructing control data is to eliminate pattern-matching biases formed by LLMs during large-scale pre-training. Large language models often exhibit hypersensitivity to certain keywords (e.g., os.system, eval, exec), tending to issue vulnerability verdicts directly without analyzing context filtering logic. This behavior leads to a high false alarm rate. Introducing control data forces the model to distinguish the essential differences between valid security defense logic (e.g., parameterization, whitelist validation) and invalid defense logic (e.g., non-recursive replacement, blacklists). Furthermore, control data serves as the basis for calculating the "Pairwise Correct Ratio" (PCR) metric; only when a model can simultaneously and accurately distinguish between the vulnerable version and the secure version under the same functional logic is it considered to possess true secure semantic understanding capability.
2.4.2 Construction of Control Data
The construction process consists of vulnerability point identification, defense logic reconstruction, and manual verification stages. First, we deeply analyzed 105 vulnerability samples to identify critical nodes triggering risks. Subsequently, targeting Python language characteristics, we wrote corresponding defense logic and ensured that the repaired code maintained tool callability and functional integrity under the MCP protocol. Finally, all generated secure samples underwent cross-manual review to ensure no residual logical vulnerabilities existed, achieving a 1:1 logical correlation with the vulnerability samples.
This dataset follows the principle of minimal perturbation for the development of control data. Structurally, the secure control version maintains extremely high similarity to the corresponding vulnerable version. Except for the core vulnerable execution path or input sanitization logic, the remaining framework initialization code, tool definitions, and non-critical code remain identical. This design ensures that the model cannot guess based on statistical features such as code length, function names, or variable names, but must focus on specific logic differences at the code level. Meanwhile, regarding repair logic, this paper adopted industry-recognized best practices. For command injection risks, parameterized array calls or forced escaping were adopted; for SQL injection, database driver-level parameterized queries were used; for path traversal, path normalization comparison and base directory anchoring were employed. This design not only provides an evaluation benchmark but also serves as a code demonstration.

\subsection{Metrics}


\textbf{Precision and Recall.} Precision evaluates the proportion of true vulnerabilities among those identified by the model. Recall reflects the proportion of correctly detected vulnerabilities among all ground-truth vulnerabilities. F1-score measures the harmonic mean of precision and recall, providing a balanced assessment of the model's detection performance.


\textbf{Matched Pair Accuracy.} Traditional precision and recall metrics cannot fully capture whether the model genuinely distinguishes between positive and negative samples based on underlying code semantics, or merely relies on superficial matching of specific API calls. Leveraging our paired benchmark, where each vulnerable sample is matched with its fixed counterpart, we employ Matched Pair Accuracy (MPA)~\cite{matchedpair}. A pair is deemed correct only when both instances are classified correctly. MPA thus captures the proportion of pairs for which the model simultaneously identifies the vulnerable and non-vulnerable samples correctly.
