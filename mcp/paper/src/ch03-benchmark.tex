\section{Benchmark}


We present the \bench benchmark with a detailed description of the construction process and its characteristics.


\subsection{Benchmark Construction}

To construct our benchmark, we apply a four-step process. The containing samples are of the Python language, which is the dominant language in the current MCP ecosystem (95\% of the ecosystem share)~\cite{hasan2025model}.

\textbf{(1) Vulnerability Type Collection.} To understand the prevalent vulnerability types in existing MCP-based systems, we analyzed publicly disclosed vulnerabilities in the National Vulnerability Database (NVD)~\cite{nist_nvd}. Using the keyword ``MCP'', we identified 34 vulnerable MCP servers. Our analysis reveals four dominant vulnerability categories: remote code execution (RCE), denial of service (DoS), SQL injection (SQLi), and insecure file operations (IFO). In addition, we reference the OWASP OWASP LLM Top 10~\cite{owasptop10} to complement our classification. Given that MCP servers typically have access to sensitive data and external resources, we additionally include sensitive information disclosure (SID) as a relevant risk category. The remaining nine risk types in the OWASP LLM Top 10 are excluded, as they are not directly applicable to MCP server architectures.


\textbf{(2) Vulnerability-Triggering Expression Collection.} We collect vulnerability-triggering expressions (e.g., function calls) corresponding to the five identified vulnerability types.


\begin{itemize}[leftmargin=*]

    \item \textbf{Remote Code Execution (RCE).} We construct RCE vulnerabilities by introducing unsafe system shell invocations and dynamic code evaluation calls into the MCP codebase. For system shell invocation, we select calls including \texttt{os.system()}, \texttt{subprocess.run(shell=True)}, \texttt{subprocess.call()}, and \texttt{asyncio.} \texttt{create\_subprocess\_shell()} with unsanitized user input, thereby enabling direct shell command injection. In addition, we incorporate the use of ctypes to invoke the underlying \texttt{libc.system()} function, further expanding the attack surface at the native C++ library layer. For dynamic code execution, we introduce calls to \texttt{exec()}, \texttt{eval()}, \texttt{timeit.timeit()}, and \texttt{runpy.run\_path()} to construct scenarios that permit arbitrary Python code execution. Furthermore, we include expression evaluation through \texttt{pandas.query()}, which can also lead to code injection if improperly handled.

Specifically, we simulate cases involving the retrieval of email contents (\todo{The MCP server directly feeds unsanitized email content, which contains malicious instructions, into the LLM's context through a return statement}) and log files (\todo{\texttt{re.sub() and return f.read()}}), as well as the copying of sensitive data from private locations to publicly accessible directories (\texttt{shutil.copy()}).

    \item \textbf{Insecure File Operation (IFO).} Insecure file operations (IFO) encompass both path traversal and improper file permission management. For path traversal, we construct attack scenarios by invoking the unfiltered \texttt{open()} function with inputs containing \texttt{../} sequences or URL-encoded traversal patterns to bypass directory constraints. We further exploit the path-overwriting behavior of \texttt{os.path.join()} when handling absolute paths, inconsistencies in path resolution via \texttt{pathlib.Path()}, and unintended file enumeration caused by wildcard expansion in \texttt{glob.glob()}. Improper file permission and access control issues include unauthorized file deletion through \texttt{os.remove()} and \texttt{shutil.rmtree()}, insecure permission modification using \texttt{os.chmod()}, arbitrary file reading via \texttt{linecache.getline()}, unrestricted symbolic link traversal during directory walking (e.g., \texttt{os.walk()}), and time-of-check-to-time-of-use (TOCTOU) race conditions arising from the gap between link validation (e.g., \texttt{os.path.islink()}) and subsequent file access (e.g., \texttt{open()}).

    \item \textbf{Denial of Service (DoS).} DoS attacks primarily exhaust computational (e.g., CPU), memory, and storage resources. For computational exhaustion, we construct scenarios involving vulnerable regular expressions (e.g., \texttt{re.match()} or \texttt{re.compile()}) susceptible to Regular Expression Denial of Service (ReDoS), as well as unbounded computations such as \texttt{math.factorial()} or deeply recursive functions without input size constraints, which may lead to stack overflows. For memory exhaustion, we include cases such as reading the full contents of an expanded ZIP bomb via \texttt{zipfile.ZipFile.read()} and performing unconstrained string multiplications that trigger excessive memory allocation. Regarding disk resource exhaustion, we simulate file descriptor leaks (e.g., repeatedly invoking \texttt{open()} without corresponding \texttt{close()} calls) and unbounded log writing through uncontrolled \texttt{f.write()} operations, both of which can deplete disk space. At the business logic level, we model infinite execution flows, including non-terminating pagination loops (e.g., always returning a newly generated \texttt{uuid.uuid4()} as the \texttt{next\_page\_token}), dynamically fabricated directory trees that expand indefinitely for arbitrary input paths, and circular authentication deadlocks in which tools return instructions that recursively invoke one another.
 
\end{itemize}


\textbf{(3) Varying Context Insertion.} We apply multiple varying contexts surrounding the vulnerability-triggering expressions to ensure the robustness and generalization ability of the dataset in complex real-world scenarios. 





\begin{itemize}[leftmargin=*]
    \item \textbf{Encoding Variants.} We incorporate multiple encoding techniques to evaluate detector robustness. Specifically, we apply hexadecimal (Hex) and Base64 encodings, which are commonly used to represent binary data in text-based formats and to standardize cryptographic hash outputs. These transformations allow us to assess whether detectors can correctly identify semantically equivalent vulnerabilities expressed in encoded variants.
    
    \item \textbf{Dynamic Invocation.} We employ Python reflection to dynamically resolve and invoke system functions, such as constructing system call references through \texttt{getattr()}, thereby obscuring direct API usage.
 
    \item \textbf{Incomplete defenses.} We construct a series of samples with intentionally incomplete defenses to simulate common developer cognitive biases in implementing filtering logic. For RCE and SQLi, MCP servers adopt a fragile single-pass blacklist sanitization strategy (e.g., invoking \texttt{replace()} once without recursive processing), which fails to block keywords crafted through double-write nesting or mixed-case obfuscation. For insecure file operations, we model flawed path sanitization mechanisms in which URL-decoded inputs undergo only a single-pass removal of traversal patterns (e.g., applying \texttt{unquote()} followed by a single \texttt{replace("../", "")}), as well as imprecise prefix validation that relies on \texttt{startswith()} over joined but non-normalized paths. These implementations fail to account for canonicalization inconsistencies and path equivalence issues. Finally, we simulate covert fallback vulnerabilities, where the MCP server reverts to unsafe operations when secure mechanisms fail. For example, upon a \texttt{ValueError} triggered by strict type casting (e.g., \texttt{int()} conversion), the system falls back to string-based SQL query construction (e.g., f-strings), thereby reintroducing injection risks.

\textbf{(4) Vulnerable MCP Server Generation.} We employ Gemini-1.5-Pro~\cite{gemini} as the base model and design a structured prompt template incorporating persona configuration (Python Security Expert), core logic parameterization, and JSONL output constraints. Specifically, it dynamically instantiates predefined vulnerability categories, trigger logic, and variant techniques to produce diverse yet controlled risk scenarios. \textbf{(5) Vulnerable MCP Server Fixing.} We fix MCP vulnerabilities by type. For RCE, we remove user-controlled execution flows, replacing shell-based APIs (e.g., \texttt{os.system()}) with parameterized subprocess calls (\texttt{shell=False}) and substituting dynamic execution primitives (e.g., \texttt{exec()}, \texttt{eval()}) with predefined dispatch logic. Unsafe deserialization (e.g., \texttt{pickle}) is replaced with data-only formats (e.g., JSON), and strict input validation with canonicalization confines external data. For sensitive information disclosure, we enforce separation between data and instructions via structured JSON, role-label sanitization, parameter whitelists, and bounded outputs. Insecure File Operations are mitigated with a “normalize-then-validate” sandboxing: paths are canonicalized (\texttt{abspath()}, \texttt{resolve()}) and checked against a base directory, with symlink validation, multi-pass decoding, and secure temporary file APIs. For DoS, we enforce deterministic limits on recursion, iteration, memory, and decompression, optimize regex patterns against ReDoS, use non-blocking asynchronous execution, and set explicit termination conditions to prevent infinite loops. SQLi is prevented via parameterized queries, whitelisted identifiers, strict type validation, and elimination of unsafe fallback logic, ensuring data is isolated from executable commands.

\subsection{Metrics}


\textbf{Precision and Recall.} Precision evaluates the proportion of true vulnerabilities among those identified by the model. Recall reflects the proportion of correctly detected vulnerabilities among all ground-truth vulnerabilities. F1-score measures the harmonic mean of precision and recall, providing a balanced assessment of the model's detection performance.


\textbf{Matched Pair Accuracy.} Traditional precision and recall metrics cannot fully capture whether the model genuinely distinguishes between positive and negative samples based on underlying code semantics, or merely relies on superficial matching of specific API calls. Leveraging our paired benchmark, where each vulnerable sample is matched with its fixed counterpart, we employ Matched Pair Accuracy (MPA)~\cite{matchedpair}. A pair is deemed correct only when both instances are classified correctly. MPA thus captures the proportion of pairs for which the model simultaneously identifies the vulnerable and non-vulnerable samples correctly.
