\subsection{Root Cause Analysis}\label{sec:root}

We mined GitHub Issues and Stack Overflow questions related to deployment failures, filtering for issues tagged with deployment keywords, questions with accepted answers and high vote counts, and recent issues (2022-2024) to ensure relevance. This process identified 140 common deployment challenges with verified solutions.

% \subsubsection{Error Characteristics and Patterns}

We analyze key characteristics that influence deployment difficulty:

\textbf{Dependency Depth Distribution.} Most errors occur at depth 2-4 (68.3\% of cases), where indirect dependencies create conflicts. Shallow errors (depth 1, 21.4\%) are typically straightforward missing packages, while deep dependency issues (depth 5+, 10.3\%) require extensive resolution chains involving transitive dependencies.

\textbf{Root Cause Categories.} We classify scenarios by underlying causes: version mismatches (34.5\%), missing configurations (26.7\%), system-level issues like permissions and paths (18.9\%), resource conflicts such as port collisions (12.3\%), and documentation gaps representing undocumented requirements (7.6\%).

\textbf{Fix Pattern Distribution.} Solutions fall into four categories: command execution only (42.1\%) for package installation and service management, configuration file modification (31.8\%) for editing JSON/YAML/XML files, multi-step sequential fixes (19.4\%) requiring ordered resolution, and environment configuration (6.7\%) for setting variables and creating files.

\textbf{Log Characteristics.} Error messages span 1-50 lines (median: 12), with varying clarity. We include explicit error messages (67.2\%) with clear indicators and implicit failures (32.8\%) requiring deeper investigation. Primary log sources are build logs (38.4\%), runtime logs (49.9\%), and system monitoring logs (11.7\%).

\subsubsection{Error Injection}

To maximize realism, reproducibility, and controllability, each task includes a carefully crafted setup configuration that establishes the initial environment state and systematically injects realistic deployment errors:

\begin{enumerate}
\item \textbf{File preparation}: Project files are downloaded into a designated workspace directory ($\sim$/workspace/) with proper directory structure, mirroring fresh project clones from version control

\item \textbf{Controlled error injection}: Setup scripts systematically inject realistic errors that cause deployment failures. This is the \textit{core mechanism} of our benchmark design. Injection strategies include:
\begin{itemize}
    \item \textit{Dependency manipulation}: Modifying package manifests (package.json, requirements.txt, pom.xml) to introduce version conflicts or remove critical dependencies
    \item \textit{Configuration corruption}: Altering configuration files to contain invalid values, wrong paths, or missing required parameters
    \item \textit{Environment tampering}: Setting incorrect environment variables, removing required variables, or creating conflicting system configurations
    \item \textit{Permission modification}: Changing file/directory permissions to trigger access-denied errors during deployment
    \item \textit{Resource conflicts}: Pre-occupying ports, creating file locks, or consuming resources to simulate conflicts
\end{itemize}

\end{enumerate}

\subsection{Evaluation}

We evaluate GUI agents on two primary dimensions: \textbf{task success rate} and \textbf{efficiency in terms of interaction steps}, both benchmarked against human performance to provide meaningful context.

\subsubsection{Metrics}

\textbf{Success Rate.} The success rate measures the percentage of tasks an agent completes correctly according to the execution-based validation criteria (Section~\ref{sec:task-construction}). 


\textbf{Interaction Efficiency (Step Count)} To assess operational efficiency, we count the total number of atomic GUI or terminal interactions required to complete each task, including mouse clicks, keystrokes, command executions, and file edits.
