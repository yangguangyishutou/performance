\section{Benchmark}\label{sec:benchmark}

We construct a comprehensive benchmark that systematically evaluates GUI agents on real-world deployment scenarios. Our benchmark emphasizes realistic error conditions, diverse technology stacks, execution-based validation, and controllable environments.

\subsection{Open Source Software Collection}\label{sec:data-collection}

We systematically collected real-world deployment scenarios from open-source projects to ensure diversity and practical relevance. Our collection process follows a rigorous, reproducible methodology designed to capture authentic deployment challenges.

\subsubsection{Project Selection Criteria}

We applied the following quantitative filters to identify suitable projects from GitHub:

\textbf{Popularity Threshold.} We selected projects with $\geq 300$ GitHub stars, indicating active community usage and sufficient real-world deployment history. 

\textbf{Recent Activity Filter.} We required projects to have at least one commit after January 1, 2023, ensuring:
\begin{itemize}
    \item Compatibility with modern dependency versions and deployment practices
    \item Active maintenance and ongoing community support
    \item Relevance to current technology ecosystems
    \item Exclusion of abandoned projects with outdated or deprecated dependencies
\end{itemize}

\textbf{Technology Stack Diversity.} To ensure comprehensive coverage, we systematically sampled projects across major technology categories:
\begin{itemize}
    \item Web frameworks: Node.js/Express, Django/Flask/FastAPI, Spring Boot
    \item Containerization: Docker, Docker Compose, Kubernetes manifests
    \item Microservices architectures with multiple interdependent services
    \item Data processing: Apache Spark, Airflow, data pipelines
    \item Machine learning: PyTorch, TensorFlow, model serving applications
    \item Database-backed applications: MySQL, PostgreSQL, MongoDB, Redis
    \item Full-stack applications with frontend and backend components
\end{itemize}

Using GitHub's REST API v3 with query parameters \texttt{stars:>=300 pushed:>=2023-01-01}, we systematically retrieved repositories sorted by star count within each technology category. This initial search yielded \textbf{1,247 candidate repositories}.

\subsubsection{Deployment Complexity Assessment}

To ensure our benchmark evaluates meaningful debugging scenarios rather than trivial deployments, we performed manual complexity assessment. We operationalize \textbf{deployment complexity} using the following criteria:

\textbf{Inclusion Criteria} (a project must satisfy \textit{at least one} of the following):
\begin{itemize}
\item \textbf{Multi-component architecture}: Requires $\geq 2$ interdependent services (e.g., web server + application server + database, or frontend + backend + cache layer)
\item \textbf{Non-trivial configuration}: Contains configuration files (e.g., \texttt{.env}, \texttt{config.yaml}, \texttt{application.properties}) requiring environment-specific customization (database URLs, API keys, port assignments, file paths)
\item \textbf{Substantial dependencies}: Lists $\geq 5$ direct dependencies in package manifest files (\texttt{package.json}, \texttt{requirements.txt}, \texttt{pom.xml}, \texttt{Cargo.toml})
\item \textbf{Build/compilation requirements}: Requires explicit build steps beyond simple package installation (e.g., webpack bundling, Maven compilation, asset pipeline execution, binary compilation)
\item \textbf{System-level dependencies}: Depends on system libraries, specific OS packages, environment variables, or requires installation of additional software (e.g., \texttt{libpq-dev}, \texttt{redis-server}, specific Java/Node.js versions)
\end{itemize}

\subsection{Root Cause Analysis}\label{sec:root}

We mined GitHub Issues and Stack Overflow questions related to deployment failures, filtering for issues tagged with deployment keywords, questions with accepted answers and high vote counts, and recent issues (2022-2024) to ensure relevance. This process identified 140 common deployment challenges with verified solutions.

% \subsubsection{Error Characteristics and Patterns}


\textbf{Root Cause Categories.} We classify deployment scenarios into five fundamental categories based on their underlying causes:

\textbf{(1) Version Mismatches (34.5\%).} The most prevalent category involves incompatible dependency versions, including direct package conflicts (e.g., TensorFlow 2.x vs 1.x API changes), transitive dependency incompatibilities, and build tool version requirements (e.g., CMake $\geq$ 3.15 for certain features). These often manifest as cryptic import errors or compilation failures.

\textbf{(2) Missing Configurations (26.7\%).} Environment-specific settings that are absent or incorrectly specified, including environment variables (PATH, PYTHONPATH, LD\_LIBRARY\_PATH), configuration files (.env, config.yaml), and API keys or credentials. These errors typically occur at runtime rather than build time.

\textbf{(3) System-Level Issues (18.9\%).} Platform-dependent problems arising from OS differences (Linux vs Windows vs macOS), missing system libraries (libssl, CUDA drivers), compiler toolchain availability (GCC, MSVC), file system permissions, and path resolution inconsistencies (case sensitivity, path separators).

\textbf{(4) Resource Conflicts (12.3\%).} Runtime collisions including port binding conflicts, shared resource contention (GPU memory, file locks), process limits, and disk space exhaustion. These are particularly common in containerized environments and CI/CD pipelines.

\textbf{(5) Documentation Gaps (7.6\%).} Undocumented prerequisites, implicit assumptions about the deployment environment, missing setup steps in README files, and outdated installation instructions that no longer match current package versions.

\subsubsection{Error Injection}

To maximize realism, reproducibility, and controllability, each task includes a carefully crafted setup configuration that establishes the initial environment state and systematically injects realistic deployment errors:

\begin{enumerate}
\item \textbf{File preparation}: Project files are downloaded into a designated workspace directory ($\sim$/workspace/) with proper directory structure, mirroring fresh project clones from version control

\item \textbf{Controlled error injection}: Setup scripts systematically inject realistic errors that cause deployment failures. This is the \textit{core mechanism} of our benchmark design. Injection strategies include:
\begin{itemize}
    \item \textit{Dependency manipulation}: Modifying package manifests (package.json, requirements.txt, pom.xml) to introduce version conflicts or remove critical dependencies
    \item \textit{Configuration corruption}: Altering configuration files to contain invalid values, wrong paths, or missing required parameters
    \item \textit{Environment tampering}: Setting incorrect environment variables, removing required variables, or creating conflicting system configurations
    \item \textit{Permission modification}: Changing file/directory permissions to trigger access-denied errors during deployment
    \item \textit{Resource conflicts}: Pre-occupying ports, creating file locks, or consuming resources to simulate conflicts
\end{itemize}

\subsection{Evaluation}

We evaluate GUI agents on two primary dimensions: \textbf{task success rate} and \textbf{efficiency in terms of interaction steps}, both benchmarked against human performance to provide meaningful context.

\subsubsection{Metrics}

\textbf{Success Rate.} The success rate measures the percentage of tasks an agent completes correctly according to the execution-based validation criteria (Section~\ref{sec:task-construction}). 


\textbf{Interaction Efficiency (Step Count)} To assess operational efficiency, we count the total number of atomic GUI or terminal interactions required to complete each task, including mouse clicks, keystrokes, command executions, and file edits.
