\section{Empirical Study}

We conduct an empirical study to systematically examine the effectiveness and limitations of large language models for repository-level C++-to-Java translation.

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1}: How is the effectiveness of large language models in repository-level C++-to-Java translation?
\item \textbf{RQ2}: What are the common error patterns in large language model-driven repository-level C++-to-Java translation?
\end{itemize}

\subsection{Setup}

\textbf{Initial Project and Modules.} We retrieved open-source Java projects from GitHub using the query expression ``language:java size:<5000 sort:stars-desc''. This query specifies Java as the primary programming language, restricts the repository size to under 5,000 KB to facilitate manual analysis, and ranks the results in descending order by star count to prioritize more popular projects. We collected projects from the first \todo{XX} pages of the search results and excluded those unsuitable for C++ translation: (1) educational or tutorial projects containing toy examples; (2) Android applications with platform-specific dependencies; and (3) frameworks with sophisticated design patterns that is hard to create counterparts in C++ (e.g., the Spring framework which is annotation-intensive that heavily rely on reflection). As a result, we collected six open-source projects spanning diverse domains:

\begin{itemize}[leftmargin=*]
\item \textbf{failsafe}\footnote{https://github.com/failsafe-lib/failsafe}: A fault tolerance library for building resilient distributed systems.
\item \textbf{jvm-sandbox}\footnote{https://github.com/alibaba/jvm-sandbox}: An AOP (Aspect-Oriented Programming) framework for runtime code manipulation.
\item \textbf{easyexcel}\footnote{https://github.com/alibaba/easyexcel}: A library for Excel file processing with simplified APIs.
\item \textbf{httpclient}\footnote{https://github.com/wso2/wso2-commons-httpclient}: An HTTP client library for network communication.
\item \textbf{hutool}\footnote{https://github.com/dromara/hutool}: A comprehensive Java utility library.
\item \textbf{Java-WebSocket}\footnote{https://github.com/TooTallNate/Java-WebSocket}: A WebSocket implementation for real-time communication.
\end{itemize}

As the project may have multiple independent and separated modules, we perform module analysis to aggregate files into modules. Specifically, we iterate each Java source file, parse each Java source file into the AST representation using JavaParser~\cite{javaparse}, and obtain their import statements as well as the used types that do not need import statements in the same directory. We resolve the imported types into the corresponding Java source file. Upon completion of this process, the interconnected source files are partitioned into multiple clusters, each representing a logically coherent module that implements a specific and self-contained functionality. Overall, we identified 24 modules encompassing diverse source files and methods. A detailed summary of the dataset is presented in Table~\ref{tab:dataset_info}.

\textbf{Selected Modules.} For our empirical study, we randomly sampled three representative modules. i.e., \texttt{EnableJUnit4MigrationSupport} from \texttt{junit5}, \texttt{Cookie} from \texttt{httpclient}, and \texttt{CircuitBreakerExecutor} from \texttt{failsafe}. The selected modules represent varying levels of scale, including a small-scale module (8 files and 93 methods in Cookie), a medium-scale module (23 files and 141 methods in CircuitBreakerExecutor), and a large-scale module (\todo{32 files and 234 methods in EnableJUnit4MigrationSupport}). In total, the three modules include 468 methods. Based on a standard sample size calculation~\cite{sample}, this sample size ensures a 95\% confidence level with a 4.2\% margin of error relative to the overall population of 3,165 methods.

\textbf{Subject LLMs.} We selected three popular and state-of-the-art large language models. i.e., \textbf{DeepSeek-V3.2}, \textbf{Qwen-3.5Plus} and \textbf{ChatGPT-5.1}.



\textbf{Translation Strategies.} As an entire module may exceed the model's context window limitations, segmentation is required prior to translation. We evaluate two representative segmentation strategies that reflect common developer practices:

\begin{itemize}[leftmargin=*]
\item \textbf{File-by-file translation}: Each Java source file is translated independently as a self-contained unit. This strategy preserves the class structure, member declarations, and intra-file method relationships; however, it may overlook dependencies across files.
\item \textbf{Method-by-method translation}: Each Java method is translated in isolation, enabling finer-grained control over the translation process but sacrificing contextual information related to class structure and inter-method dependencies.
\end{itemize}


\textbf{RQ1 Setup.} To address translation effectiveness (RQ1), we implemented a three-step evaluation pipeline. First, we translated all Java files in the selected modules using both strategies using file-by-file translation, and all Java methods using method-by-method translation, \todo{including member variables of each class that are translated separately.} Then, we compiled the translated Java file using clang++~\cite{clang} 20.1.8 compiler with -c flag. \todo{For the translated methods, we concatenated the translated methods along with translated member variables into the C++ file and then used the clang++ compiler.} Finally, we recorded the compilation outcomes (success/error) generated from clang++. A file is considered successfully compiled when the compiler produces a corresponding object file (.o) without fatal errors.

We observe that all three models struggle with repository-level translation, with success rates ranging from 1.09\% to 19.32\%. This reveals a significant gap between the capabilities of current LLMs and the requirements of real-world project translation tasks.


\textbf{Impact of Segmentation Strategy.} Comparing the two segmentation schemes, method-by-method translation consistently outperforms file-by-file translation across all models except Qwen-3.5Plus. Specifically:
\begin{itemize}[leftmargin=*]
\item \textbf{DeepSeek-V3.2}: 15.1\% (file-by-file) vs 16.6\% (method-by-method), +2.4\% improvement
\item \textbf{Qwen-3.5Plus}: 13.4\% (file-by-file) vs 15.1\% (method-by-method), -2.4\% decrease
\item \textbf{ChatGPT-5.1}: 15.1\% (file-by-file) vs 21.4\% (method-by-method), +4.8\% improvement
\end{itemize}

ChatGPT-5.1 benefits the most from finer-grained translation, showing a 6.3\% improvement with method-by-method strategy. DeepSeek-V3.2 also shows moderate improvement (+1.5\%), while Qwen-3.5Plus performs almost equally under both strategies.

\textbf{Impact by Project.} As shown in Figure~\ref{fig:empirical_success_by_project_class} and Figure~\ref{fig:empirical_success_by_project_method}, the translation effectiveness varies significantly across different projects. The Cookie module achieves the highest success rate (23.8\% for file-by-file, 33.3\% for method-by-method) due to its extremely simple structure, while CircuitBreakerExecutor shows the lowest success rate (7.7\% for both strategies). The EnableJUnit4MigrationSupport module achieves an intermediate success rate of 12.1\%. This indicates that domain complexity and API usage patterns affect the LLM's translation capability. Notably, larger project size does not necessarily correlate with lower success rates: EnableJUnit4MigrationSupport (32 files) achieves a higher success rate than the smaller CircuitBreakerExecutor module (23 files).

\textbf{Method-Level Error Analysis.}
Figure~\ref{fig:empirical_error_method} presents the distribution of error types at the method level.
The most prevalent error is \textsc{Missing/Undefined Symbols}, affecting 17.90\% of translated methods on average. This error occurs when the LLM generates code that references functions, classes, or standard library components that do not exist or are not properly included.
The second most common error is \textsc{Type System Error} (5.27\%), which involves mismatches between expected and actual types, incorrect pointer conversions, or improper handling of C++ specific type features like \texttt{const} correctness and reference semantics.
Other notable errors include \textsc{Build/Include Error} (1.93\%), \textsc{Redefinition Error} (1.35\%), and \textsc{Syntax Error} (0.82\%).

\textbf{Class-Level Error Analysis.}
Figure~\ref{fig:empirical_error_class} reveals a markedly different error distribution at the class (file) level.
The two most dominant errors are \textsc{Build/Include Error} (72.28\%) and \textsc{Missing/Undefined Symbols} (67.24\%). The high prevalence of build/include errors at the class level indicates that LLMs frequently struggle with generating proper header guard structures, include directives, and headers across multiple files within a translation unit.
\textsc{Type System Error} remains significant at 32.50\%, while \textsc{Template Error} (12.11\%) and \textsc{Syntax Error} (10.87\%) also appear frequently.
Notably, \textsc{Inheritance/Virtual Error} (6.37\%) and \textsc{Redefinition Error} (4.82\%) emerge as class-level concerns, reflecting challenges in translating complex C++ object-oriented features such as virtual function tables, multiple inheritance, and method overriding.

\textbf{Strategy Comparison.}
Regarding the translation strategy, method-by-method translation generally reduces class-level structural errors (e.g., build/include errors and template errors) since each method is translated independently without requiring file-level context. However, this strategy may increase method-level symbol resolution errors due to the lack of surrounding class context. File-by-file translation preserves class structure better but introduces more opportunities for compilation failures due to header organization and include directive issues.

\textbf{Key Findings.}
The error pattern analysis reveals three key findings:
(1) \textit{Symbol resolution is the primary bottleneck}: The high prevalence of missing/undefined symbol errors across both levels indicates that LLMs struggle to maintain consistent symbol tables and API mappings during translation.
(2) \textit{C++ specific features remain challenging}: Template errors, inheritance/virtual function errors, and type system errors collectively account for a significant portion of failures, suggesting that LLMs need specialized handling for C++ language features that have no Java equivalents.
(3) \textit{File-level organization is a critical failure point}: The high rate of build/include errors at class level highlights the importance of proper header management and build system configuration---aspects that are often overlooked in translation but are essential for successful compilation.
