\section{Empirical Study}

We conduct an empirical study to systematically examine the effectiveness and limitations of large language models for repository-level C++-to-Java translation.

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1}: How is the effectiveness of large language models in repository-level C++-to-Java translation?
\item \textbf{RQ2}: What are the common error patterns in large language model-driven repository-level C++-to-Java translation?
\end{itemize}

\subsection{Setup}

\textbf{Initial Project and Modules.} We retrieved open-source Java projects from GitHub using the query expression ``language:java size:<5000 sort:stars-desc''. This query specifies Java as the primary programming language, restricts the repository size to under 5,000 KB to facilitate manual analysis, and ranks the results in descending order by star count to prioritize more popular projects. We collected projects from the first \todo{XX} pages of the search results and excluded those unsuitable for C++ translation: (1) educational or tutorial projects containing toy examples; (2) Android applications with platform-specific dependencies; and (3) frameworks with sophisticated design patterns that is hard to create counterparts in C++ (e.g., the Spring framework which is annotation-intensive that heavily rely on reflection). As a result, we collected six open-source projects spanning diverse domains:

\begin{itemize}[leftmargin=*]
\item \textbf{failsafe}\footnote{https://github.com/failsafe-lib/failsafe}: A fault tolerance library for building resilient distributed systems.
\item \textbf{jvm-sandbox}\footnote{https://github.com/alibaba/jvm-sandbox}: An AOP (Aspect-Oriented Programming) framework for runtime code manipulation.
\item \textbf{easyexcel}\footnote{https://github.com/alibaba/easyexcel}: A library for Excel file processing with simplified APIs.
\item \textbf{httpclient}\footnote{https://github.com/wso2/wso2-commons-httpclient}: An HTTP client library for network communication.
\item \textbf{hutool}\footnote{https://github.com/dromara/hutool}: A comprehensive Java utility library.
\item \textbf{Java-WebSocket}\footnote{https://github.com/TooTallNate/Java-WebSocket}: A WebSocket implementation for real-time communication.
\end{itemize}

As the project may have multiple independent and separated modules, we perform module analysis to aggregate files into modules. Specifically, we iterate each Java source file, parse each Java source file into the AST representation using JavaParser~\cite{javaparse}, and obtain their import statements as well as the used types that do not need import statements in the same directory. We resolve the imported types into the corresponding Java source file. Upon completion of this process, the interconnected source files are partitioned into multiple clusters, each representing a logically coherent module that implements a specific and self-contained functionality. Overall, we identified 24 modules encompassing diverse source files and methods. A detailed summary of the dataset is presented in Table~\ref{tab:dataset_info}.

\textbf{Selected Modules.} For our empirical study, we randomly sampled three representative modules. i.e., \texttt{EnableJUnit4MigrationSupport} from \texttt{junit5}, \texttt{Cookie} from \texttt{httpclient}, and \texttt{CircuitBreakerExecutor} from \texttt{failsafe}. The selected modules represent varying levels of scale, including a small-scale module (8 files and 93 methods in Cookie), a medium-scale module (23 files and 141 methods in CircuitBreakerExecutor), and a large-scale module (\todo{32 files and 234 methods in EnableJUnit4MigrationSupport}). In total, the three modules include 468 methods. Based on a standard sample size calculation~\cite{sample}, this sample size ensures a 95\% confidence level with a 4.2\% margin of error relative to the overall population of 3,165 methods.

\textbf{Subject LLMs.} We selected three popular and state-of-the-art large language models. i.e., \textbf{DeepSeek-V3.2}, \textbf{Qwen-3.5Plus} and \textbf{ChatGPT-5.1}.



\textbf{Translation Strategies.} As an entire module may exceed the model's context window limitations, segmentation is required prior to translation. We evaluate two representative segmentation strategies that reflect common developer practices:

\begin{itemize}[leftmargin=*]
\item \textbf{File-by-file translation}: Each Java source file is translated independently as a self-contained unit. This strategy preserves the class structure, member declarations, and intra-file method relationships; however, it may overlook dependencies across files.
\item \textbf{Method-by-method translation}: Each Java method is translated in isolation, enabling finer-grained control over the translation process but sacrificing contextual information related to class structure and inter-method dependencies.
\end{itemize}


\textbf{RQ1 Setup.} To address translation effectiveness (RQ1), we implemented a three-step evaluation pipeline. First, we translated all Java files in the selected modules using both strategies using file-by-file translation, and all Java methods using method-by-method translation, \todo{(member variables of each class are alse translated separately.)}. We measure the effectiveness of translation using the \textbf{compilation success rate (CSR)}, defined as the percentage of successfully compiled C++ files or methods relative to the total number of files or methods.

Figure~\ref{fig:empirical_success_rate} presents the overall effectiveness across different LLMs and segmentation strategies. We observe that all three models struggle with repository-level translation, with success rates ranging from \todo{13.4\%} to \todo{21.4\%}. This reveals a significant gap between the capabilities of current LLMs and the requirements of real-world project translation tasks.


\textbf{Impact of Segmentation Strategy.} Comparing the two segmentation schemes, method-by-method translation consistently outperforms file-by-file translation across all models. Specifically:
\begin{itemize}[leftmargin=*]
\item \textbf{DeepSeek-V3.2}: 15.1\% (file-by-file) vs 16.6\% (method-by-method)
\item \textbf{Qwen-3.5Plus}: 13.4\% (file-by-file) vs 15.1\% (method-by-method)
\item \textbf{ChatGPT-5.1}: 15.1\% (file-by-file) vs 21.4\% (method-by-method)
\end{itemize}
