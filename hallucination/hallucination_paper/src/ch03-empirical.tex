\section{Empirical Study}

We conduct an empirical study to systematically examine the effectiveness and limitations of large language models for repository-level C++-to-Java translation.

Given that repositories may exceed model input limits, segmentation of the source code is required prior to translation. We consider two representative segmentation schemes that reflect common developer usage scenarios when applying large language models: \textit{(a) File-by-file translation}. Each source file is translated independently without explicit cross-file contextual information. \textit{(b) Method-by-method translation.} Each C++ method (function) is translated independently, allowing finer-grained control while sacrificing broader cross-method context awareness.

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1}: How is the effectiveness of large language models in repository-level C++-to-Java translation using representative segmentation schemes?
\item \textbf{RQ2}: What are the common failure patterns in repository-level C++-to-Java translation using large language models?
\end{itemize}

\subsection{Setup}

\textbf{Dataset.}
We selected four real-world Java projects from open-source repositories to evaluate the translation performance. These projects span multiple domains to ensure diverse scenarios:
\begin{itemize}[leftmargin=*]
\item \textbf{wso2-commons-httpclient}\footnote{https://github.com/wso2/commons-httpclient}: An HTTP client library (Cookie module), representing network communication utilities.
\item \textbf{failsafe}\footnote{https://github.com/failsafe-lib/failsafe}: A fault tolerance library (CircuitBreakerExecutor and RateLimiterExecutor modules), representing resilience patterns for distributed systems.
\item \textbf{junit5}\footnote{https://github.com/junit-team/junit5}: A testing framework (EnableJUnit4MigrationSupport module), representing testing infrastructure and migration utilities.
\end{itemize}

\textbf{Subject Models.}
We evaluated three state-of-the-art large language models:
\begin{itemize}[leftmargin=*]
\item \textbf{DeepSeek-V3.2}: An open-weight model with strong code generation capabilities.
\item \textbf{Qwen-3.5Plus}: A model optimized for programming tasks.
\item \textbf{ChatGPT-5.1}: A proprietary model with advanced reasoning abilities.
\end{itemize}

\textbf{Evaluation Metric.}
We measure translation effectiveness using \textbf{compilation success rate}, defined as the percentage of successfully generated C++ files that compile without errors. A file is considered successfully translated only if it produces a valid compilation with no syntax errors, type mismatches, missing dependencies, or other build failures.

\textbf{Procedure.}
For each model and segmentation scheme, we translated all Java files in the selected projects and attempted to compile the generated C++ code. We manually analyzed compilation failures and categorized errors into distinct types to identify systematic failure patterns. It is important to note that our manual analysis focuses on understanding the distribution and characteristics of identified problems, which reveal fundamental challenges in LLM-based code translation, rather than providing a complete enumeration of all possible defects.

\subsection{Effectiveness (RQ1)}

Figure~\ref{fig:empirical-success-rate} presents the overall translation success rates across different models and segmentation strategies.

\begin{figure}[h]
\centering
\includegraphics[width=0.85\textwidth]{figures/empirical_success_rate.pdf}
\caption{Overall translation success rates by model and strategy.}
\label{fig:empirical-success-rate}

\textbf{Key Findings:}

\begin{enumerate}[leftmargin=*]
\item \textbf{Low overall effectiveness}: Across all models and strategies, the highest success rate achieved was only 16.4\% (Qwen-3.5Plus with file-by-file translation). This demonstrates that current LLMs struggle significantly with repository-level C++-to-Java translation, even when using the most favorable segmentation approach.

\item \textbf{File-by-file outperforms method-by-method}: The file-by-file strategy consistently achieves higher success rates than method-by-method translation across all models. For example, DeepSeek-V3.2 achieves 10.4\% success with file-by-file but only 6.0\% with method-by-method. Similarly, Qwen-3.5Plus drops from 16.4\% to 1.5\% when switching strategies. This suggests that preserving intra-file context (class structure, field declarations, method signatures) is critical for maintaining translation coherence.

\item \textbf{Model performance varies significantly}: Qwen-3.5Plus demonstrates the best performance with file-by-file translation (16.4\%), followed by DeepSeek-V3.2 (10.4\%) and ChatGPT-5.1 (7.5\%). However, with method-by-method translation, all models converge to similarly low performance (1.5--6.0\%), indicating that segmentation strategy has a larger impact than model choice for this task.

\item \textbf{Project-specific variations}: As shown in Figure~\ref{fig:empirical-success-by-project}, translation effectiveness varies substantially across projects. The Cookie module achieves the highest success rate (up to 44.4\% with Qwen-3.5Plus file-by-file), while CircuitBreakerExecutor consistently fails (0\% success for most configurations). This variation correlates with project complexity: simpler utility classes with fewer dependencies translate more successfully than complex modules with intricate inheritance hierarchies and extensive cross-file dependencies.

\begin{figure*}[h]
\centering
\includegraphics[width=\textwidth]{figures/empirical_success_by_project.pdf}
\caption{Translation success rates by project, model, and strategy.}
\label{fig:empirical-success-by-project}
\end{figure*}

\item \textbf{Method-by-method strategy consistently fails}: The method-by-method approach shows near-zero success rates across most projects and models. For instance, RateLimiterExecutor achieves 0\% success with all models using method-by-method translation, compared to 5.6--11.1\% with file-by-file. This severe degradation indicates that translating methods in isolation, without visibility into class structure and related method implementations, introduces fatal inconsistencies that prevent compilation.
\end{enumerate}

These findings collectively demonstrate that repository-level translation remains an open challenge for LLMs. The low success rates highlight fundamental limitations in current models' ability to (1) maintain global consistency across multiple translation units, (2) handle complex cross-file dependencies, and (3) preserve type-system correctness when operating on segmented inputs.

\subsection{Failure Patterns (RQ2)}

To understand the root causes of translation failures, we systematically categorized compilation errors into 11 distinct types based on error symptoms and underlying mechanisms. Figure~\ref{fig:empirical-error-heatmap} presents the distribution of the most common error types across models and strategies.

\begin{figure}[h]
\centering
\includegraphics[width=0.9\textwidth]{figures/empirical_error_heatmap.pdf}
\caption{Distribution of common error types across models and strategies.}
\label{fig:empirical-error-heatmap}
\end{figure}

\textbf{Dominant Error Types:}

\begin{enumerate}[leftmargin=*]
\item \textbf{Build and Include Errors (55.8\%)}: The most prevalent failure mode involves missing header files, incorrect include directives, and build system configuration issues. This occurs because LLMs lack awareness of the project-wide include structure when translating individual files. For example, a translated C++ class may reference types from another translated file without including the appropriate header, leading to ``undefined type'' compilation errors.

\item \textbf{Missing and Undefined Symbols (41.7\%)}: This category encompasses references to functions, variables, or classes that are declared but never defined, or referenced without any declaration. In method-by-method translation, this frequently occurs when a method calls another method that has not yet been translated or is defined in a separate file not visible to the model. Even with file-by-file translation, cross-file method calls often result in undefined references because the model cannot ensure consistent naming and signatures across translation boundaries.

\item \textbf{Type System Errors (26.6\%)}: These errors manifest as type mismatches in variable declarations, function parameters, return values, and implicit conversions. Common patterns include:
\begin{itemize}[leftmargin=*]
\item Incorrectly mapping Java collection types to C++ templates (e.g., \texttt{ArrayList<T>} $\rightarrow$ \texttt{std::vector<T>} without proper instantiation syntax)
\item Failing to propagate const-correctness through method chains
\item Inconsistent type mapping between related files (e.g., using \texttt{String} in one file and \texttt{std::string} in another)
\end{itemize}

The higher prevalence of type errors in file-by-file translation (38.8\% vs. 14.5\% in method-by-method) suggests that preserving class structure exposes type system inconsistencies that are hidden when methods are translated in isolation.

\item \textbf{Syntax and Language Feature Errors (7.8\%)}: These errors indicate fundamental misunderstandings of C++ syntax, including:
\begin{itemize}[leftmargin=*]
\item Incorrect template syntax (e.g., missing \texttt{typename} keywords, malformed template parameters)
\item Semicolon placement and statement termination
\item Improper use of C++-specific keywords (e.g., \texttt{virtual}, \texttt{override}, \texttt{constexpr})
\end{itemize}

While less common than build or symbol errors, syntax errors are particularly problematic because they prevent compilation even when the overall translation approach is sound.

\item \textbf{Redefinition Errors (6.8\%)}: Redefinition occurs when the same symbol (function, variable, or class) is defined multiple times across different translation units. This is especially common in file-by-file translation when multiple files independently translate the same utility class or inline function, leading to linker errors. The higher rate of redefinition errors in file-by-file translation (8.4\% vs. 5.1\%) reflects this duplication challenge.

\item \textbf{Inheritance and Virtual Function Errors (4.9\%)}: These errors involve incorrect handling of C++ object-oriented features, such as:
\begin{itemize}[leftmargin=*]
\item Missing \texttt{virtual} keywords on overridden methods
\item Incorrect base class initialization lists in constructors
\item Failure to declare pure virtual methods in abstract base classes
\item Mismatched access specifiers (public/protected/private) in derived classes
\end{itemize}

The significantly higher rate in file-by-file translation (8.9\% vs. 0\%) indicates that when class hierarchies are preserved, models struggle to correctly translate inheritance relationships and maintain virtual function consistency across parent and child classes.
\end{enumerate}

\textbf{Strategy-Specific Patterns:}

Figure~\ref{fig:empirical-error-stacked} reveals distinctive error profiles for each segmentation strategy.

\begin{figure*}[h]
\centering
\includegraphics[width=\textwidth]{figures/empirical_error_stacked.pdf}
\caption{Error type distribution by model and strategy.}
\label{fig:empirical-error-stacked}
\end{figure*}

\begin{itemize}[leftmargin=*]
\item \textbf{File-by-file}: Dominated by type system errors (38.8\%), reflecting the challenge of maintaining type consistency when translating complete class declarations. The higher inheritance error rate (8.9\%) confirms that translating class hierarchies exposes object-oriented design misunderstandings. Build/include errors remain prevalent (55.3\%) due to cross-file header dependencies.

\item \textbf{Method-by-method}: Characterized by missing/undefined symbol errors (44.9\%), as translating methods in isolation breaks call chains and type dependencies. The lower type error rate (14.5\%) is misleading—rather than indicating better type handling, it suggests that methods fail earlier due to missing symbols before type mismatches can manifest.
\end{itemize}

\textbf{Implications:}

The error distribution analysis reveals that translation failures are not random but stem from systematic limitations:
\begin{enumerate}[leftmargin=*]
\item \textbf{Context fragmentation}: Segmentation breaks the global coherence required for successful translation, causing build errors and missing definitions that cannot be resolved without project-wide awareness.
\item \textbf{Inconsistency propagation}: Small inconsistencies in type mapping, naming conventions, or API design compound across translation boundaries, creating cascading failures that are difficult to trace and fix.
\item \textbf{Lack of dependency awareness}: Models cannot reliably determine correct translation order or ensure that dependencies are satisfied before use, leading to undefined symbols and incomplete definitions.
\end{enumerate}

These findings motivate the need for a translation framework that (1) maintains global project context, (2) establishes consistent conventions before translating individual units, and (3) uses dependency-aware ordering to prevent missing symbol errors—design principles that directly inform our approach presented in Section~\ref{sec:approach}.
