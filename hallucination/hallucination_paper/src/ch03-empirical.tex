\section{Empirical Study}

We conduct an empirical study to systematically examine the effectiveness and limitations of large language models for repository-level C++-to-Java translation.

\begin{itemize}[leftmargin=*]
\item \textbf{RQ1}: How is the effectiveness of large language models in repository-level C++-to-Java translation?
\item \textbf{RQ2}: What are the common failure patterns in large language model-driven repository-level C++-to-Java translation?
\end{itemize}

\subsection{Setup}

\textbf{Dataset.} To construct a comprehensive evaluation dataset, we collected open-source Java projects from GitHub using systematic selection criteria. Our inclusion criteria required: (1) Java as the primary development language; (2) Project size under 5,000 KB to ensure tractability; (3) High popularity measured by star count to ensure real-world relevance. We excluded projects unsuitable for C++ translation: (1) Educational or learning projects with toy examples; (2) Android applications with platform-specific dependencies; (3) Annotation-heavy frameworks relying on reflection (e.g., Spring), which lack direct C++ equivalents.

We collected six open-source projects spanning diverse domains:

\begin{itemize}[leftmargin=*]
\item \textbf{failsafe}\footnote{https://github.com/failsafe-lib/failsafe}: A fault tolerance library for building resilient distributed systems.
\item \textbf{jvm-sandbox}\footnote{https://github.com/alibaba/jvm-sandbox}: An AOP (Aspect-Oriented Programming) framework for runtime code manipulation.
\item \textbf{easyexcel}\footnote{https://github.com/alibaba/easyexcel}: A library for Excel file processing with simplified APIs.
\item \textbf{httpclient}\footnote{https://github.com/wso2/wso2-commons-httpclient}: An HTTP client library for network communication.
\item \textbf{hutool}\footnote{https://github.com/dromara/hutool}: A comprehensive Java utility library.
\item \textbf{Java-WebSocket}\footnote{https://github.com/TooTallNate/Java-WebSocket}: A WebSocket implementation for real-time communication.
\end{itemize}

To balance translation quality evaluation with practical scale constraints, we extracted fully functional modules from these projects as translation units. As shown in Algorithm~\ref{alg:getDependencyFiles}, we perform dependency traversal starting from a seed file, recursively collecting all dependent files to form a self-contained module. This approach ensures that each module maintains complete functionality while remaining of manageable size. We extracted 24 modules containing 8--35 files each, with 469 Java files and 3,165 methods in total. Table~\ref{tab:dataset_info} summarizes the complete dataset.

\begin{algorithm}
\label{alg:getDependencyFiles}
\caption{Dependency-Based Module Extraction}
\begin{algorithmic}[1]
\Function{getDependencyFiles}{$project$, $file$}
    \State $dependencies$ $\gets$ \{$file$\}
    \If{$file$ has no dependencies}
        \State \Return $dependencies$
    \EndIf
    \For{$f$ in $project$}
        \If{$f$ depends on $file$}
            \State $dependencies$ $\gets$ $dependencies$ $\cup$ \Call{getDependencyFiles}{$project$, $f$}
        \EndIf
    \EndFor
    \State \Return $dependencies$
\EndFunction
\end{algorithmic}
\end{algorithm}

\textbf{Subject Models.} We evaluated three state-of-the-art large language models.

\begin{itemize}[leftmargin=*]
    \item \textbf{DeepSeek-V3.2}: An open-weight model with strong code generation capabilities.
    \item \textbf{Qwen-3.5Plus}: A model optimized for programming tasks.
    \item \textbf{ChatGPT-5.1}: A proprietary model with advanced reasoning abilities.
\end{itemize}

\textbf{Evaluation Metric.}
We measure translation effectiveness using \textbf{compilation success rate}, defined as the percentage of generated C++ source files that compile successfully without errors. Specifically, we combine all generated C++ source files (.cpp) and header files (.h), then compile each source file separately. A file is considered successfully compiled when the compiler produces a corresponding object file (.o) without fatal errors. The compilation success rate is calculated as:

$$ \text{Success Rate} = \frac{\text{Number of Successfully Compiled .cpp Files}}{\text{Total Number of .cpp Files}} \times 100\% $$

This metric directly reflects the functional correctness of generated code, as uncompilable code cannot be executed or tested.

\textbf{Translation Strategies.}
Since repositories may exceed model context window limits, code segmentation is necessary before translation. We evaluate two representative segmentation strategies reflecting common developer workflows:

\begin{enumerate}[leftmargin=*]
\item \textbf{File-by-file translation}: Each Java source file is translated independently as a complete unit. This approach preserves class structure, member declarations, and intra-file method relationships, but may miss cross-file dependencies.
\item \textbf{Method-by-method translation}: Each Java method is translated in isolation, providing finer-grained control but sacrificing contextual information about class structure and inter-method relationships.
\end{enumerate}

These strategies represent endpoints on the granularity spectrum, allowing us to evaluate how context scope affects translation quality.

\textbf{RQ Setup.}
To address \textbf{RQ1} (translation effectiveness), we implemented a three-step evaluation pipeline: (1) Translated all Java files in the selected modules using each strategy; (2) Attempted compilation of generated C++ code using clang++ 20.1.8 compiler with -c flag to focus on syntax and type correctness without linking; (3) Recorded binary compilation outcomes (success/failure) and calculated compile success rates. To explore \textbf{RQ2} (failure pattern analysis), we conducted systematic manual analysis of compilation failures at the method granularity. For files that failed compilation, we extracted individual method implementations and compiled them in isolation to isolate specific failure points. Iteratively refining categories based on recurring patterns in compiler error messages. Keyword analysis of clang++ output (e.g., "undefined reference", "no matching function", "type mismatch") provided initial categorization cues. Once all failure pattern is determined, we assign a categorized tag to each method that fails to compile (a single method may have multiple types of error tags). It is important to note that our manual analysis focuses on understanding the distribution and characteristics of identified problems, which reveal fundamental challenges in LLM-based code translation, rather than providing a complete enumeration of all possible defects. This targeted approach ensures we capture the most impactful failure patterns while maintaining feasibility given the dataset size.

\subsection{Translation Effectiveness (RQ1)}

Figure~\ref{fig:empirical_success_rate} presents the overall compilation success rates across different models and segmentation strategies. We observe that all three models struggle with repository-level translation, with success rates ranging from 1.09\% to 19.32\%. This reveals a significant gap between the capabilities of current LLMs and the requirements of real-world project translation tasks.

\begin{figure*}[htbp]
\centering
\includegraphics[width=0.85\textwidth]{figures/empirical_success_rate.pdf}
\caption{Overall compilation success rates by model and segmentation strategy. File-by-file translation generally outperforms method-by-method across all models.}
\label{fig:empirical_success_rate}
\end{figure*}

\textbf{Impact of Segmentation Strategy.} Comparing the two segmentation schemes, file-by-file translation consistently outperforms method-by-method translation across all models. Specifically:
\begin{itemize}[leftmargin=*]
\item \textbf{DeepSeek-V3.2}: 10.29\% (file-by-file) vs 4.73\% (method-by-method)
\item \textbf{Qwen-3.5Plus}: 19.32\% (file-by-file) vs 1.09\% (method-by-method)
\item \textbf{ChatGPT-5.1}: 7.43\% (file-by-file) vs 6.04\% (method-by-method)
\end{itemize}

The superior performance of file-by-file translation can be attributed to better preservation of contextual information. When translating entire files, models maintain awareness of class structures, member variable declarations, and inter-method relationships within the same compilation unit. In contrast, method-by-method translation isolates individual functions, forcing the model to infer dependencies without explicit context, leading to inconsistencies in type usage, API calls, and naming conventions.

\textbf{Model Performance.} Qwen-3.5Plus achieves the highest overall success rate at 19.32\% under file-by-file translation, followed by DeepSeek-V3.2 (10.29\%) and ChatGPT-5.1 (7.43\%). However, Qwen-3.5Plus exhibits extreme variance between strategies (19.32\% vs 1.09\%), indicating high sensitivity to segmentation granularity. This suggests that model architecture and training data significantly influence translation robustness across different input scopes.

\textbf{Project-Level Analysis.} Figure~\ref{fig:empirical_success_by_project} reveals substantial variation in difficulty across translation units. The Cookie module from wso2-commons-httpclient achieves the highest average success rate (12.96\%), while CircuitBreakerExecutor from failsafe proves most challenging (1.96\%). The EnableJUnit4MigrationSupport module demonstrates relatively stable performance (13.04\%) across most configurations.
\begin{figure*}[htbp]
\centering
\includegraphics[width=0.95\textwidth]{figures/empirical_success_by_project.pdf}
\caption{Compilation success rates across different projects. Performance varies significantly by translation unit, reflecting differences in code complexity and domain-specific patterns.}
\label{fig:empirical_success_by_project}
\end{figure*}
Several factors contribute to this variance:
\begin{itemize}[leftmargin=*]
\item \textbf{Code complexity}: Modules with deeper inheritance hierarchies (e.g., CircuitBreakerExecutor) present more translation challenges due to virtual function dispatch and abstract base class dependencies.
\item \textbf{External dependencies}: Projects heavily reliant on third-party libraries (e.g., HTTP client utilities) introduce uncertainty when mapping Java APIs to C++ equivalents.
\end{itemize}
\textbf{Key Findings for RQ1.}
\begin{enumerate}[leftmargin=*]
\item Current LLMs achieve low compilation success rates (1--20\%) for repository-level translation, indicating substantial limitations in handling real-world project complexity.
\item File-by-file translation outperforms method-by-method by 2--18$\times$, highlighting the critical importance of contextual breadth for maintaining translation consistency, however, for larger files, the model's handling of the details of each method may be somewhat biased..
\item Success rates vary significantly across projects (1.96--13.04\%), suggesting that code complexity, domain patterns, and external dependencies are key factors influencing translation difficulty.
\item Even the best-performing configuration (Qwen-3.5Plus, file-by-file) succeeds on fewer than 1 in 5 files, underscoring the need for improved translation methodologies.
\end{enumerate}

\subsection{Failure Patterns (RQ2)}

To understand the root causes of translation failures, we systematically categorized compilation errors and analyzed their distribution. Figure~\ref{fig:empirical_error_by_type} presents the error type occurrence rates across all model-strategy combinations, revealing consistent patterns that transcend specific model architectures.

\begin{figure*}[htbp]
\centering
\includegraphics[width=0.95\textwidth]{figures/empirical_error_by_type_horizontal.pdf}
\caption{Error type occurrence rate by model and translation strategy. Each bar group shows the percentage of methods containing each error type, with different colors representing different model-strategy configurations. Build/Include and Missing Symbols errors dominate across all configurations.}
\label{fig:empirical_error_by_type}
\end{figure*}

\textbf{Error Type Taxonomy.} We systematically categorized all compilation errors into 11 distinct types based on their underlying causes:

\begin{enumerate}[leftmargin=*]
\item \textbf{Build/Include Errors}: Missing header files, incorrect include directives, and dependency resolution failures.
\item \textbf{Missing/Undefined Symbols}: References to undeclared functions, variables or classes.
\item \textbf{Type System Errors}: Type mismatches, incorrect type conversions,and incomplete type definitions.
\item \textbf{Syntax/Language Errors}: Violations of C++ syntax rules, improper use of language constructs, and semantic errors that prevent parsing.
\item \textbf{Declaration/Definition Mismatch}: Inconsistencies between function signatures in headers and their implementations, or mismatched parameter lists.
\item \textbf{Inheritance/Virtual Errors}: Issues related to virtual function overriding, abstract class implementations, and inheritance hierarchy problems.
\item \textbf{Redefinition Errors}: Multiple definitions of the same variable, function, or class, often due to missing include guards or improper header structure.
\item \textbf{Access Scope Errors}: Violations of access control rules (public/private/protected), incorrect friend declarations, and scope resolution failures.
\item \textbf{Constructor/Destructor Errors}: Problems with constructor initialization, destructor implementation, and resource management lifecycle issues.
\item \textbf{Template Errors}: Template declaration syntax errors, instantiation failures, and template parameter deduction problems.
\item \textbf{Other Errors}: Compilation failures that do not fit into the above categories.
\end{enumerate}

\textbf{Dominant Error Categories.} Across all configurations, three error categories account for the majority of methods failing compilation:

\begin{enumerate}[leftmargin=*]
\item \textbf{Build/Include Errors} This error category stems from three primary challenges:
\begin{itemize}[leftmargin=*]
\item \textit{Missing header files}: Sometimes the model does not include the corresponding header file when using classes from standard library.
\item \textit{Java-to-C++ mapping uncertainty}: For many classes in the Java standard library, such as Serializable and Comparator, the model cannot correctly map them to appropriate C++ classes.
\item \textit{Header file hallucination} Due to misleading import statements in Java code, models sometimes include header files that do not exist (for example, Java's Date class is often mapped to a file named 'Date.h', which does not exist in the C++ standard library).
\end{itemize}

\item \textbf{Missing or Undefined Symbols} This category encompasses:
\begin{itemize}[leftmargin=*]
\item \textit{Untranslated dependencies}: When translating a method, models may reference methods from other classes that were translated with different signatures.
\item \textit{Fragmented type definitions}: Forward declarations may be omitted, or definitions may be split across headers incorrectly, causing redefinition errors.
\end{itemize}

\item \textbf{Type System Errors} 
\begin{itemize}[leftmargin=*]
\item \textit{Unsupported overload}: Some unsupported overloaded methods were used. For example, cannot stream std::exception\_ptr directly with operator<<.
\item \textit{Unsupported type conversion}: Some unsupported types were used. For example, cannot convert std::unique\_ptr to std::string.
\item \textit{Wrong return type}: Incorrect return value types were returned.
\end{itemize}
\end{enumerate}

Figure~\ref{fig:empirical_error_stacked} illustrates the relative composition of error types across configurations.

\begin{figure*}[htbp]
\centering
\includegraphics[width=0.9\textwidth]{figures/empirical_error_stacked.pdf}
\caption{Stacked error distribution by configuration. Each bar shows the percentage of methods containing each error type. Build/Include and Missing Symbols dominate across all model-strategy combinations.}
\label{fig:empirical_error_stacked}
\end{figure*}

\textbf{Model-Specific Patterns.} While overall error distributions are similar, subtle differences emerge:
\begin{itemize}[leftmargin=*]
\item \textbf{Qwen-3.5Plus} exhibits higher Type System error rates (affecting over 99\% methods in file-by-file strategy), suggesting weaker reasoning about generic type mappings and template constraints.
\item \textbf{DeepSeek-V3.2} shows elevated Missing Symbols errors in file-by-file strategy (affecting over 70\% methods), indicating difficulty maintaining API consistency across complex inheritance hierarchies.
\item \textbf{ChatGPT-5.1} demonstrates relatively balanced error distribution but with consistently high Build/Include errors (affecting over 60\% methods), reflecting challenges in header dependency resolution.
\end{itemize}

\textbf{Strategy-Dependent Variations.} Comparing segmentation strategies:
\begin{itemize}[leftmargin=*]
\item \textbf{File-by-file} results in fewer methods with Missing Symbols errors on average, confirming that broader context helps maintain API consistency.
\item \textbf{Method-by-method} generates more Redeclaration and Definition Mismatch errors, likely due to translating methods without visibility of existing declarations in headers.
\item Both strategies exhibit comparable Build/Include error rates , indicating that header dependency resolution remains challenging regardless of segmentation granularity.
\end{itemize}
