\section{Empirical Study}

This section presents a comprehensive study of the performace of LLMs on real-world Java projects. Without employing complex dependency analysis and other enhancement methods, there are two naive translation schemes:

\textbf{File-level Translation}: File-by-file translation using LLMs with minimal context.

\textbf{Method-level Translation}: Method-by-method translation using LLMs with minimal context.

\subsection{Research Questions}

Our study addresses the following research questions:

\begin{itemize}
\item \textbf{RQ1}: What are the main problems that arise during the translation process using these two methods?
\item \textbf{RQ2}: What is the problems distribution of these two methods?
\item \textbf{RQ3}: How does the performance compare between File-level and Method-level Translation?
\end{itemize}

\subsection{Results}

\subsubsection{RQ1: Main Problems in Translation}

Through manual code analysis, we identified and categorized 11 distinct types of translation problems. Table~\ref{tab:error-categories} summarizes these problem types with descriptions and examples.

\begin{table*}[h]
\centering
\small
\begin{tabular}{p{0.5cm}p{8cm}p{5cm}}
\toprule
\textbf{Type} & \textbf{Problem Description} & \textbf{Example} \\
\midrule
Err\_1 & Reference to non-existent methods or member variables & Calling \texttt{getCause()} on \texttt{std::exception} \\
Err\_2 & Parameter signature mismatch & Wrong parameter types in function calls \\
Err\_3 & Missing header files & Using \texttt{std::set} without \texttt{<set>} \\
Err\_4 & Method completely unimplemented & Declaration provided but no implementation \\
Err\_6 & Variable initialization/usage errors & Reference members not initialized \\

\bottomrule
\end{tabular}
\caption{Categories of translation problems identified}
\label{tab:error-categories}
\end{table*}

The most prevalent problem types are:
\begin{itemize}
\item \textbf{Err\_9 (Non-existent class references)}: This occurs most frequently because LLMs often hallucinate Java-standard-library classes (e.g., \texttt{Date}, \texttt{Comparator}) that have no direct C++ equivalents. The model assumes these classes exist in the target environment without verifying C++ standard library availability.

\item \textbf{Err\_1 (Non-existent method/variable references)}: LLMs generate method calls or member accesses assuming Java API semantics, but the corresponding C++ APIs either do not exist or have different signatures. For example, calling \texttt{getCause()} on \texttt{std::exception}—a method that exists in Java but not in C++.

\item \textbf{Err\_2 (Parameter mismatch)}: Method calls are generated with incorrect parameter types or counts, indicating that the LLM fails to maintain consistency between function signatures and their usage sites.
\end{itemize}

These problems stem from a fundamental limitation: \textbf{LLMs translate code in isolation without awareness of the broader codebase context}. When translating individual files or methods, the model lacks visibility into:
\begin{itemize}
\item Which classes and methods have already been translated elsewhere
\item The correct C++ type mappings chosen for other parts of the project
\item Consistent API signatures established in previously translated code
\end{itemize}

This contextual vacuum leads to hallucination and generating code that appears syntactically plausible but references non-existent APIs or uses inconsistent translations of the same concept.

\subsubsection{RQ2: Problem Distribution}

We analyzed the distribution of problems across both translation methods. Figure~\ref{fig:error-distribution} shows the frequency of each error type.

\begin{figure*}[h]
\centering
\includegraphics[width=0.9\textwidth]{figures/comparison.png}
\caption{Error type distribution in File-level vs Method-level translation}
\label{fig:error-distribution}
\end{figure*}

\textbf{Key observations:}

\begin{enumerate}
\item \textbf{Dominance of class-reference errors (Err\_9)}: Both translation methods exhibit Err\_9 as the most frequent problem, accounting for 4.2\% of File-level translations and 6.7\% of Method-level translations. This suggests that LLMs struggle significantly with mapping Java's rich standard library to C++'s more minimal standard library.

\item \textbf{Consistent error patterns}: The relative ranking of error types is similar across both methods, indicating that these problems are \textit{intrinsic} to the translation task rather than artifacts of a specific translation scheme.

\item \textbf{Variation by module complexity}: Modules with deeper inheritance hierarchies exhibited higher problem rates compared to utility classes . This correlation suggests that complex object-oriented structures exacerbate LLM translation difficulties.
\end{enumerate}

\textbf{Findings:}

\begin{enumerate}
\item \textbf{File-level translation exhibits fewer detected problems}: The File-level approach showed 9.0\% of translations with detected problems, compared to 14.0\% for Method-level—a 5.0 percentage point difference. This suggests that providing more context (the entire file rather than individual methods) helps reduce hallucinations.

\item \textbf{Method-level shows higher error frequency in most categories}: As shown in Figure~\ref{fig:error-distribution}, Method-level translation produced more errors in 9 out of 11 problem categories. Notably:
\begin{itemize}
\item Err\_9 (non-existent classes): +31 occurrences
\item Err\_2 (parameter mismatch): +8 occurrences
\item Err\_10 (partial implementation): +9 occurrences
\end{itemize}

\item \textbf{Trade-offs in granularity}: While Method-level translation provides finer-grained error isolation (making issues easier to locate), it sacrifices the contextual coherence that File-level translation maintains. The data shows that this contextual deprivation manifests as more frequent API inconsistencies and hallucinated references.
\end{enumerate}

\subsection{Discussion: Limitations of Naive Translation Approaches}

Our empirical study reveals fundamental challenges in applying LLMs to repository-level code translation using naive file-level or method-level approaches:

\begin{enumerate}
\item \textbf{Context fragmentation}: Both translation schemes suffer from incomplete context. File-level translation sees only intra-file dependencies, while Method-level translation sees even less. This fragmentation causes:
\begin{itemize}
\item Inconsistent translations of the same concept across different files/methods
\item Failure to leverage already-translated code as reference
\item Hallucination of APIs that should have been mapped from existing translations
\end{itemize}

\item \textbf{Lack of dependency awareness}: Neither approach considers the call graph or inheritance hierarchy when determining translation order. Consequently:
\begin{itemize}
\item Callee methods may be translated after their callers, preventing consistent API usage
\item Base classes may be translated after derived classes, causing inheritance mismatches
\item Translation decisions made early cannot inform later translations
\end{itemize}

\item \textbf{No validation feedback loop}: Both approaches generate code without verification. Compilation errors, type mismatches, and API inconsistencies remain unaddressed until manual review.
\end{enumerate}
