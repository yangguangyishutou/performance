\subsection{Data Collection}
We collect our dataset through a two-step process. First, we identify CWE entries associated with overflow vulnerabilities. Then, we extract relevant vulnerability samples from widely-used vulnerability repair datasets based on these identified CWEs.

\sloppy
To systematically identify overflow-related vulnerabilities, we adopt a two-pronged approach to collecting relevant CWE entries. First, we refer to the Common Weakness Enumeration (CWE) framework\cite{CWEHome}, specifically utilizing CWE View-1000\cite{CWE1000}, also known as the “Research Concepts View.” This view provides a semantically organized structure of software weaknesses tailored for academic analysis, emphasizing conceptual clarity and hierarchy. Based on this taxonomy, we identify CWE-119 — Improper Restriction of Operations within the Bounds of a Memory Buffer — and its descendant nodes as representative of overflow vulnerabilities. The complete list of selected CWE entries is provided in Table~\ref{tab:cwe-list}.Second, to complement the taxonomy-driven selection, we conduct a survey of recent research on vulnerability detection and repair. Using keywords such as “overflow,” “detect,” and “repair,” we search for papers published in top-tier software engineering and security venues (e.g., CCS\footnote{ACM Conference on Computer and Communications Security}, ASE\footnote{IEEE/ACM International Conference on Automated Software Engineering}). From these works\cite{le2024study,li2022pacmem,liu2025cctag,zhang2023vulnerability,kang2022tracer,gorter2024sticky,steenhoek2023empirical,ba2022efficient,guo2024precise}, we analyze the datasets used and extract the CWE identifiers associated with overflow vulnerabilities. We find that most of these CWEs are already included in the CWE View-1000 hierarchy; for those not covered, we incorporate them into our list to ensure comprehensive coverage and consistency with real-world research practices.

Next, we extract overflow-related vulnerability samples from two widely used vulnerability repair datasets: BigVul\cite{bigvul} and CVEFixes\cite{bhandari2021:cvefixes}. BigVul is a large-scale dataset that collects real-world vulnerabilities and corresponding fixes from open-source projects hosted on GitHub. CVEFixes, on the other hand, focuses on Common Vulnerabilities and Exposures (CVEs) and provides fine-grained fix commits associated with specific CVE entries. To maintain consistency with BigVul, we only retain C/C++ vulnerability samples from CVEFixes.We merge the two datasets following the standard practice established in prior work\cite{zhou2024large}, including deduplication and partitioning at the function level. Before filtering, the merged dataset consists of \textcolor{red}{XXX} CWEs, \textcolor{red}{XXX} CVEs, and \textcolor{red}{XXX} vulnerable functions. By applying the set of CWE identifiers identified in the previous step, we construct a refined dataset focused on overflow vulnerabilities, which includes \textcolor{red}{XXX} distinct CVEs and \textcolor{red}{XXX} vulnerable functions.A detailed breakdown of the final dataset is presented in Table~\ref{tab:cwe-distribution}.

In addition, we analyze the distribution of the number of vulnerable functions associated with each CVE, as shown in Table~\ref{tab:cve-func-dist}. The results indicate that \textcolor{red}{XXX} CVEs contain only a single vulnerable function, accounting for\textcolor{red}{XXX}\%, while \textcolor{red}{XXX} CVEs involve multiple vulnerable functions, accounting for \textcolor{red}{XXX}\%. Existing studies have largely focused on repairing single-function vulnerabilities, often simplifying multi-function vulnerabilities into single-function cases for processing. However, repairing multi-function vulnerabilities is inherently more challenging: when reduced to the single-function level, large language models lack sufficient contextual information, making correct repairs infeasible. Therefore, directly simplifying multi-function vulnerabilities into single-function cases is problematic. In this work, we further analyze, through an empirical study, the impact of these unrepairable multi-function vulnerabilities on overall repair performance.

\subsection{RQ1: Vulnerability Repairability}
Based on prior research, a multi-function vulnerability may include functions that are unrelated to the actual repair. These functions often remain logically equivalent before and after the fix, serving mainly to improve code readability rather than contributing to the repair itself. Among the functions that are directly related to the repair, we further distinguish between two categories: functions that are repairable from a single-function perspective and those that are not. The former refers to cases where the vulnerability trigger logic can be inferred solely from the code of the function, enabling effective repair. The latter, by contrast, refers to cases where the vulnerability trigger logic cannot be deduced from the function alone, making it impossible to repair in isolation. Clearly, functions that are unreparable from a single-function perspective necessarily depend on contextual information provided by other functions to identify the vulnerability trigger logic and guide the repair.

Both irrelevant functions and single-function-unrepairable functions are unique challenges associated with multi-function vulnerabilities. In contrast, functions corresponding to single-function vulnerabilities are always directly related to the vulnerability and thus do not exhibit these issues. The relationships are summarized in Table~\ref{tab:func-classification}.

To analyze this phenomenon, we performed stratified sampling on our dataset, ensuring that the distribution of CWEs and the distribution of the number of functions per CVE were consistent with those of the overall dataset. For irrelevant repair functions, we exclude them from the validation set used to evaluate vulnerability-repair tools. By contrast, functions that are unrepairable when viewed in isolation are treated as an intrinsic characteristic of multi-function vulnerabilities and therefore cannot be reduced to single-function cases.

We further investigated the underlying causes of these irrelevant repair functions. Such cases may include situations where the pre- and post-repair functions are semantically equivalent and the changes merely improve code readability, or where additional functionality is introduced that is unrelated to the vulnerability fix. Functions that remain unrepairable under a single-function setting often do so because their remediation requires coordinated modifications across multiple functions, employs macro definitions, or depends on variables and contextual information that cannot be inferred from the function alone.As shown in the Table~\ref{tab:irf-ur-categories}.
